# BAL-005 — R3 Omaha / R4 5장 사전 승률 계산 기준 검증

분석 브랜치: `balance/BAL-005-latest` · 기준 커밋: `c7b2315` (REQUEST 포함 커밋 `2e4bbdd`)

이 문서는 계산 오류를 이미 확정하지 않는다. 아래 각 발견 항목은 **계산 오류 / 규칙상 올바르지만 불확실한 추정 /
표시 개선 필요 / 추가 데이터 필요** 중 하나로 분류했으며, 게임 소스·UI·공용 테스트는 전혀 수정하지 않았다.
모든 수치는 `product_doc/balance/BAL-005/artifacts/scripts/`의 스크립트가 **실제 프로덕션 함수**
(`findBestFive`, `findBestOmaha`, `compareHands`, 그리고 `showdownEquity` 자체)를 직접 호출해 얻은 결과다.
재구현(reimplementation)으로 별도 판정 로직을 만들지 않았다 — 그렇게 하면 "검증"이 아니라 "다른 버그"를
비교하는 셈이기 때문이다.

## 0. 요약 (TL;DR)

| # | 발견 | 분류 |
|---|---|---|

| 5 | `botStrategy.ts`의 R3 `scoreHeadsUp`은 고정된 상대에 대해 보드를 **2개** 뽑아 평균한다(실제 R3는 보드 1개). 실측 결과 이 평균은 단일 보드 기대값과 통계적으로 구분되지 않는다(§6) — 편향이 아니라 분산 감소 기법. | 정상 (편향 없음, 확인됨) |
| 6 | `findBestOmaha`는 "정확히 홀 2장 + 보드 3장" 제약을 5가지 적대적 케이스(포카드/트립스 함정, 보드 단독 플러시 함정, 최소 플러시 조건)에서 모두 올바르게 지킨다(§4). | 정상 (확인됨) |
| 7 | 승/무/패 → 1/0.5/0 인코딩과 `[left, 100-left]` 구조상 두 값의 합은 **항상 정확히 100**이다(반올림 방식과 무관하게 보장). | 정상 (확인됨) |

## 1. 라운드별 공식 정의 (실제 코드 기준)

### 1.1 카드 제약과 평가 함수

| 라운드 | 홀카드 | 보드 | 평가 함수 (UI `showdownEquity.ts` / 실제 `engine.ts handFor`) |
|---|---|---|---|
| R1 (Two Hand, Hold'em) | 2장 | 5장 | `findBestFive([...hole, ...board])` — 7장 중 최적 5장 |
| R3 (Omaha Swiss) | 4장 | 5장 (그중 3장만 사용) | `findBestOmaha(hole, board)` — 홀 정확히 2장 + 보드 정확히 3장의 모든 조합(6×10=60가지) 중 최고 |
| R4 (Best Five) | 5장 | 5장 | `findBestFive([...hole, ...board])` — 10장 중 최적 5장 |
| R5 (보드 없음, 참고용) | 7장 | 없음 | `findBestFive(hole)` 직접 비교, 샘플링 없이 1회 정확 계산 |

`findBestOmaha`/`findBestFive`/`compareHands`는 **엔진(`engine.ts`)과 UI(`showdownEquity.ts`)와 봇
(`botStrategy.ts`)이 전부 `src/core/poker/evaluate.ts`의 동일한 함수를 import해서 쓴다.** 판정 로직 자체가
갈라지는 지점은 코드베이스 어디에도 없다(Q1 답변: 예, 완전히 동일한 제약을 적용한다).

### 1.2 보드 수 — R3가 "두 런"이라는 가설은 기각됨

`holto-chess/src/game/engine.ts`:
```
const boardCount = state.round === 2 ? 2 : state.round === 5 ? 0 : 1;
```
`holto-chess/src/game/showdownDeck.ts`의 `drawCommunityBoards(deck, boardCount, cardsPerBoard=5)`가 이 수만큼
5장짜리 보드를 **같은 덱에서 순서대로, 서로 겹치지 않게** 뽑는다. **"두 보드 런"은 R2(RUN IT TWICE) 전용이며,
R3(Omaha Swiss)와 R4(Best Five)는 모두 보드 1개다.** REQUEST.md의 사전 가설("R3가 두 런을 쓸 가능성")은
코드로 반증된다 — `showdownEquity.ts`가 R3에서도 보드 1개만 샘플링하는 현재 동작은 **실제 규칙과 일치**한다
(Q2 답변).

### 1.3 상대 카드 표본 생성 (Q4)

`showdownEquity()`는 상대 카드를 무작위로 생성하지 않는다. `ShowdownPrepPanel.tsx`가 넘기는 `matchup.viewer.cards`,
`matchup.opponent.cards`는 **서버 상태에 이미 확정된, 실제로 그 매치에서 쓰일 홀카드 그대로**다
(`playerView.ts`가 `player.ownedCardIds`/`selectedCardIds`를 그대로 매핑). 즉 "사용자가 보는 상대 핸드"와
"계산에 쓰인 상대 핸드"는 **항상 동일한 객체**다 — 이 경로에는 불일치가 없다. 무작위로 뽑히는 것은 **보드
5장뿐**이며, 두 손이 실제로 쥔 카드를 제외한 나머지 덱에서 뽑는다(엔진의 `createShowdownDeck`과 동일하게
"이 매치의 두 참가자가 보유한 카드"만 제외 — 다른 참가자/다른 매치 카드는 제외하지 않음. 헤즈업 매치업에서는
이 차이가 결과에 영향을 주지 않는다).

### 1.4 무승부·합계 처리 (Q5)

`compareHands` 결과를 `1(승) / 0.5(무) / 0(패)`로 환산해 `leftShare`에 누적하고, 최종적으로
`leftPercent = round(leftShare*100/N)`, `rightPercent = 100 - leftPercent`로 **뺄셈으로 산출**한다. 두 값을
각각 반올림하는 것이 아니라 한쪽만 반올림하고 나머지를 100에서 빼므로, **합계는 항상 정확히 100**이 되도록
설계되어 있다(§0 표 #7, 실측으로 재확인 — 72개 케이스 전부 100).

### 1.5 표본 수와 반올림 (Q6, Q7)

`SAMPLES = { 1: 1200, 2: 1200, 3: 600, 4: 240, 5: 1(정확 계산) }`. 표본 수가 작을수록 표준오차(SE)가 커진다:

| 라운드 | SAMPLES | 근사 SE (p≈0.5 기준) | 95% CI 반폭 |
|---|---|---|---|
| R1 | 1200 | ≈1.44%p | ≈2.9%p |
| R3 | 600 | ≈2.04%p | ≈4.0%p |
| R4 | 240 | ≈3.22%p | ≈6.3%p |

R4는 정수로 반올림된 "예상 승률 57%" 같은 표시가 실제로는 ±6%p 안팎의 오차를 가질 수 있다는 뜻이며, UI에는
이 불확실성이 전혀 표시되지 않는다(§0 #3). 시드가 `` `${round}:${known 카드ids 순서대로}` `` 문자열의 FNV
해시이므로 **완전히 동일한 입력(같은 배열, 같은 순서)에 대해서는 항상 같은 결과**가 나온다(반복 실행 안정성
확인됨, §7). 문제는 순서가 바뀌면 시드가 바뀐다는 점이다(§0 #2, §7).

## 2. 방법론

- **재현 대상**: 실제 소스의 `showdownEquity`, `findBestFive`, `findBestOmaha`, `compareHands`를 Node에서
  직접 import해 실행(재구현 없음). 경로: `artifacts/scripts/lib/evalRound.ts`.
- **결정적 사례**: R1/R3/R4 각 24건(REQUEST 최소 요구 20건 이상), `artifacts/scripts/lib/cases.ts`. 강한/약한
  구조, 페어(중복 rank), suited/rainbow, connected/scattered, AAxx, 낮은/높은 카드, R4 메이드/드로우/산개를
  포함. 모든 케이스는 52장 덱 내 카드 ID 중복이 없음을 자동 검증(`validateCases`).
- **기준값(ground truth)**:
  - **전수 계산**: R1 6건, R3 4건, R4 3건(계산 비용이 커 전체 72건 전수 계산은 비현실적 — R4 한 건이 약
    10~12분 소요). `combinations()`로 잔여 덱의 모든 5장 보드 조합을 정확히 순회(표본오차 0).
    `artifacts/scripts/exactSpotCheck.ts`.
  - **대형 몬테카를로 기준**: 나머지 전 사례 R1(N=200,000)/R3(N=150,000)/R4(N=40,000), **프로덕션과 무관한
    독립 RNG**(mulberry32)로 SE·95% CI 계산. `artifacts/scripts/referenceMC.ts`.
  - 전수 계산과 대형 MC는 스팟체크 대상에서 서로 CI 안에서 일치함(교차 검증, §5).
- **실제 표시값**: `showdownEquity()`를 그대로 호출(SAMPLES·시드 포함, 수정 없음).
  `artifacts/scripts/productionEquity.ts`.
- **분류 기준**: 대형기준 CI 반폭 + (대형기준의 승률 p와 프로덕션 SAMPLES 수로 계산한) 프로덕션 자체의
  95% CI 반폭을 더한 값을 허용오차로 삼아, `|표시값 − 대형기준값| ≤ 허용오차`이면 "표본오차",
  이를 벗어나면 "계산 오류 후보"로 표시하고 원인을 재추적(`artifacts/scripts/classify.ts`). p=0.5 근사가
  아니라 각 케이스의 실제 p로 계산하므로(무승부로 인한 분산 감소까지 반영해 이항분포 p(1-p)를 상한으로
  사용, §5 참고) 케이스마다 허용오차가 다르다.

## 3. Omaha 2+3 제약 검증 (Q3) — 결과: 정상

5개의 적대적 케이스(포카드→트립스 강등, 트립스→페어 강등, 보드 단독 플러시 무효화, 홀 스페이드 1장 부족,
홀 스페이드 정확히 2장일 때의 정상 플러시)를 `findBestOmaha` vs "틀린 규칙"인 7장 중 최적 5장
(`findBestFive`)과 나란히 비교했다. 전부 통과 — `artifacts/tests/omaha_constraint_checks.log`.

가장 특징적인 사례: 홀카드에 스페이드가 0장이고 보드에 스페이드가 4~5장 떠 있어도(`findBestFive`라면
FLUSH로 오판), `findBestOmaha`는 올바르게 `HIGH_CARD`로 판정한다 — Omaha는 홀 2장을 반드시 섞어야 하므로
보드가 아무리 좋아도 소용없다는 규칙이 지켜짐을 뜻한다.

## 4. 봇의 R3 이중 보드 평균 — 편향 검증 (§0 #5)

`botStrategy.ts`의 `scoreHeadsUp`(round===3)은 고정된 헤즈업 상대에 대해 보드를 2회 뽑아(`deck.slice(0,5)`,
`deck.slice(5,10)`) 각각 비교한 뒤 평균한다. 실제 R3 쇼다운은 보드가 1개뿐이므로, 이것이 "봇이 잘못된
규칙으로 카드 가치를 계산"하는 것인지 확인해야 했다.

`artifacts/scripts/botR3TwoBoardBias.ts`는 동일한 고정 핸드 쌍에 대해 (A) 보드 1개짜리 표준 추정(N=300,000)과
(B) 봇의 실제 이중 보드 평균 루프 구조를 그대로 재현한 추정(150,000회 바깥 샘플 = 보드 평가 30만 회, 동일한
연산량)을 비교했다. 결과(`artifacts/results/bot_r3_twoboard_bias.log`):

| 케이스 | (A) 단일 보드 | (B) 봇의 이중 보드 평균 | \|A−B\| | CI 겹침 |
|---|---:|---:|---:|---|
| r3-01 AAKKds vs 876ss+5d | 58.546% [58.369, 58.722] | 58.340% [58.167, 58.514] | 0.205pp | 예 |
| r3-07 AA27 rainbow vs QJT9ds | 51.980% [51.801, 52.159] | 51.861% [51.686, 52.036] | 0.119pp | 예 |

두 케이스 모두 95% CI가 겹친다 — **편향이 아니라 분산 감소 기법일 뿐**이라는 뜻이다(두 독립 보드를
평균해도 기대값은 변하지 않는다는 표준적인 몬테카를로 성질). 결론: botStrategy의 R3 이중 보드 평균은
"봇이 다른 규칙으로 카드 가치를 계산"하는 게 아니라, 같은 단일 보드 기대값을 더 적은 분산으로 추정하는
내부 구현 디테일이다.

## 6. 반복성·순서-안정성 검증 (Q6)

- **반복성**: 동일 배열을 두 번 호출 — 72건 전부 완전히 동일한 결과(당연히 결정적 시드이므로).
- **순서-안정성**: 카드 집합은 동일하지만 배열 순서만 뒤집었을 때 — 전체 72건 중 **63건(88%)**에서
  표시값이 달라짐(R1: 24건 중 16건, R3: 24건 중 24건 전부, R4: 24건 중 23건). 최대 편차는 **11%p**
  (`r4-02`: AK94(2) vs T9876, 70%→59%). 이는 §0 #2의
  근본 원인이다: `showdownEquity`의 시드 문자열이 `known.map(c => c.id).join(":")`로, **카드 ID를 정렬하지
  않은 채** 그대로 이어 붙인다. 실제 게임에서 두 손의 카드 배열이 항상 같은 순서로 유지된다면 사용자는 이
  불안정성을 보지 못하지만, "동일한 손인데 왜 승률이 다르게 보이나"라는 사용자 체감 불일치의 **잠재적
  근본 원인**이다 — 카드 구매 순서, 리롤, 배열 재구성 등 어떤 경로로든 저장 순서가 달라지면 실제 카드 강도와
  무관하게 표시 승률이 바뀔 수 있다.

## 7. 결론 및 분류

### 7.1 "스모킹 건" 사례: `r4-16` (AAKK3 vs QQJJ6)

이 케이스가 §5·§6의 두 발견이 실제로 어떻게 겹쳐 나타나는지 가장 잘 보여준다.

- 대형 기준값(N=40,000, 독립 RNG): **65.16%** (KK/QQ 더블페어 구조에서 AAKK 쪽이 상당히 유리 — 직관과도 맞음)
- 현재 표시값(실제 배열 순서 그대로): **57%** — 기준보다 8.16%p 낮아 허용오차(6.49%p)를 벗어남
- 카드 배열만 뒤집어 같은 함수를 다시 호출하면: **67%** — 기준값과 1.84%p 차이로 오차 범위 안

즉 "AAKK vs QQJJ가 실제로는 약 65%인데 화면엔 57%로 뜨는" 현상이 실제로 재현됐고, 원인은 카드 강도 계산이
아니라 **그 특정 배열 순서가 우연히 뽑은 시드가 240개 표본 안에서 비대표적인 결과를 냈기 때문**이다. 배열
순서를 뒤집기만 해도(즉 카드 저장 순서가 달랐다면) 기준값에 훨씬 가까운 숫자가 나왔을 것이다. 이것이
REQUEST의 원 관찰("표시 승률이 가끔 실제 카드 강도와 안 맞는다")과 가장 직접적으로 맞아떨어지는 재현
사례다.

### 7.2 다중 비교 주의사항

R4에서 `r4-04`, `r4-16` 두 건이 95% 허용오차를 벗어났다. 그러나 72개의 **독립적인** 95% 신뢰구간 검정을
수행하면, 모든 계산이 완전히 정상이어도 순전히 우연으로 평균 72×0.05 ≈ 3.6건이 범위를 벗어나는 것이
통계적으로 정상이다. 따라서 "2건 이탈" 자체는 계산 로직에 문제가 있다는 증거가 아니다 — 다만 §7.1처럼
그 이탈이 **순서-불안정성과 함께** 나타나는 경우는 우연이 아니라 시드 설계의 구조적 결과로 봐야 한다
(`r4-16`은 두 문제가 겹친 사례, `r4-04`는 이탈 폭에 비해 순서를 뒤집어도 큰 변화가 없어(49→48) 순수
표본오차로 보는 편이 합리적이다).

## 8. 권고 (구현하지 않음 — 제안만)

1. `showdownEquity.ts`의 시드 문자열 생성 시 `known.map(c=>c.id)`를 **정렬 후** join — 카드 배열 순서와
   무관하게 같은 손이면 항상 같은 표시값이 나오도록 한다. 최소 변경, 로직 변경 없음(시드 재현성의 정의만
   바뀜 — 기존 회귀 테스트의 정확한 %는 바뀔 수 있으니 스냅숏 테스트 갱신 필요).
2. R4 SAMPLES(240)을 늘리는 것을 검토 — 다만 UI 렌더 타이밍(로딩 화면 노출 시간) 제약과 트레이드오프이므로
   기획 판단 필요. 대안으로 정수 % 대신 "±5%p" 같은 오차 힌트만 추가해도 사용자 오해를 줄일 수 있음.
3. (아이디어, 낮은 우선순위) R5처럼 R1/R3/R4도 조합 수가 감당 가능하면 표본 대신 정확 계산으로 전환 가능한지
   검토 — R1은 48장 중 5장(1,712,304가지)으로 클라이언트에서 실시간 계산하기엔 무겁지만, 서버에서 사전
   계산해 캐싱하는 방식은 고려해볼 만하다.

## 10. 남아 있는 위험 / 한계

- 전수 계산은 시간 비용 때문에 R1 6건·R3 4건·R4 3건에만 적용했다. 나머지는 N이 매우 큰(150k~200k) 독립
  RNG 몬테카를로이므로 이론상 아주 작은 잔차 오차가 있을 수 있으나, CI 반폭이 이미 프로덕션 SE보다 훨씬
  작아 결론에는 영향이 없다.

  순서가 실제로 얼마나 자주/어떤 조건에서 바뀌는지는 별도 조사 필요) — 다만 코드 자체의 취약점은 확정적이다.
