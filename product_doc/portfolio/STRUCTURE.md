## 목적과 형식

외부 방문자가 처음 보는 게임을 이해한 뒤, 채용 담당자가 시스템 설계와 검증 사례를 읽을 수 있는 단일 페이지 사이트. 기존 게임의 남색·청록 아레나를 사용하되 본문은 편집형 레이아웃과 절제된 타이포그래피로 읽기 쉽게 구성한다.

첫 15초: 게임 정체성, 공유 52장과 6라운드, 설계 사례 진입.
1분: 담당 역할과 대표 기획 사례 하나. 세부 라운드 설명은 사례 뒤에 배치한다.
3~5분: 문제→결정→검증→한계, AI 협업에서 개인의 역할.

## 페이지 순서

| 순서 | 섹션 | 평가할 수 있는 역량 |
|---|---|---|
| 1 | 게임의 한 문장·아레나·프로젝트 핵심 수치 | 기획 의도를 간결하게 전달 |
| 2 | 설계 질문·장르·개발 상태 | 문제 정의·프로젝트 이해 |
| 3 | R2 카드 사용 방식 개편 | 의도와 규칙·예외·검증 연결 |
| 4 | 봇 구매·리롤 조건 | 지표 설계·자원 교환·실험 해석 |
| 5 | 결승 출전 카드와 공개 규칙 | 플레이 조건·정보 공개와 화면 연결 |
| 6 | R1~R6 선택형 흐름도, 카드 획득·구매 비용·어빌리티 | 시스템 간 관계·플레이어 의사결정 |
| 7 | 의사결정·구현·검증·재검토와 AI 협업 | 협업·문서화·역할의 투명성 |
| 8 | GitHub·설계 결정·웹 프로토타입 | 근거 확인 경로 |

사례 3~5는 세 개의 선택 버튼으로 상세를 전환한다. 모바일에서는 카드 세 개를 세로로 배치하고 짧은 설명을 함께 보여준다. 면접 제출용 PDF가 필요하면 각 사례를 독립 문서로 확장한다.

## 개인 기여의 표현

문서상 사용자는 게임 방향·규칙·밸런스의 최종 승인자. Codex는 기획·개발·테스트·통합, Claude는 지정 범위 분석·구현에 참여했다. 사용자가 코드를 전부 직접 작성했다거나 실험을 직접 실행했다고 쓰지 않는다. 각 사례는 맡은 일 → 바꾸려던 점 → 정한 규칙과 조건 → 확인한 결과로 읽히게 구성한다. 구현·실험 협업 설명은 공통 역할 영역에 모으고 세부 실험 조건은 펼쳐볼 수 있게 한다. 개인 기여는 EVIDENCE.md의 사용자 지시·요청·선택·승인 추적표를 따른다.

공개 전 개인 이름·지원 소개·참여 기간·연락처를 확인한다. 연락처와 경력은 임의 작성하지 않는다. 사례별 개인 수행 범위는 개발 기록에서 확인한 내용으로 보완했다. 1인칭 문장은 기록의 재서술이며 대화 원문 인용이 아니다. 추가 면접 설명을 위한 개인 회고는 확인된 사실과 구분한다.

## 현재 자료 적용 규칙

- 현재 6라운드와 R2 세 장 전체 BEST FIVE를 사용한다. 이전 5라운드·앵커 소개 자료는 사용하지 않는다.
- R3 경매·R5 세 RUN·R6 3인 결승을 현행 규칙으로 설명한다.
- R1 A/B는 2026-10-12 당시 실험이며 최신 어빌리티 패치 재측정값이 아니다. 잔여 BB 감소·표본·실패 테스트 한계를 함께 적는다.
- QA 스크린샷은 실제 개발 화면이지만 정적 fixture임을 명시한다. 실제 사용자 대전·성과·이용자 수로 소개하지 않는다.
- 게임 배경 이미지는 플레이 화면이 아니라고 표시한다. 기존 저품질 홍보 영상은 포함하지 않는다.
- Steam Windows 출시 준비, Discord Activity, 웹이라는 출시 범위와 실제 운영 검증 상태를 구분한다. 이번 초안에 출시 확정 배지를 넣지 않는다.
