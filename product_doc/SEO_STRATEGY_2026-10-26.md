AI 사용 자체를 미색인 원인으로 단정하지 않는다. 읽는 사람에게 도움이 되는 독창적인 설명, 정확한 규칙, 실제 선택 사례가 부족한 것은 고칠 수 있다. 하지만 크롤링 이전 단계와 콘텐츠를 읽은 이후의 평가를 혼동하지 않는다.

## 3. 구글의 공개 지침을 실행으로 옮기는 방법

1. **발견·수집**: 실제 공개 URL, 정상 응답, robots 허용, 표준 a 링크, 유효한 사이트맵을 갖춘다. Search Console URL 검사에서 크롤링·렌더링·선택 canonical을 확인한다.
2. **색인**: 수집된 페이지의 주요 콘텐츠가 충분한지, 다른 페이지의 복제품이나 오류 화면이 아닌지 확인한다. HTTP 200, 소유권 확인, 사이트맵 제출만으로 색인이 보장되지는 않는다.
3. **검색어와의 관련성**: 제목·본문·링크가 같은 게임을 정확히 설명하게 한다. ‘포커’의 도박·룰·대회 탐색 의도 전체에 맞추려 하지 않는다.
4. **신뢰와 독창성**: 제작자가 알고 있는 실제 선택과 규칙을 보여준다. 다른 사이트가 자발적으로 소개할 만한 플레이 장면과 개발 기록을 만든다. 가짜 리뷰·구매 링크·수상·방문자 수를 만들지 않는다.
5. **클릭과 만족**: 제목·설명이 실제 게임과 맞아야 한다. 방문자가 즉시 무엇을 하는 게임인지 이해하고 플레이로 이동할 수 있어야 한다. CTR·체류시간을 구글의 확정 랭킹 가중치로 표현하지 않는다.

AI 말투를 지우기 위한 동의어 치환이나 분량 채우기가 아니라, 남의 게임에도 적용될 문장을 실제 PORENA의 선택으로 교체한다. 구글이 요구하는 최소 글자 수나 최적 키워드 밀도는 설정하지 않는다.

## 5. 이번 소개 페이지 구성과 구현 범위

- /about URL과 self-canonical 유지. 설명 페이지를 /로 리디렉션하거나 내용이 다른 /를 canonical로 지정하지 않는다.
- 제목: `포레나 PORENA | 패를 만드는 포커 덱빌딩 오토배틀러`.
- 첫 문장부터 규칙 분류표를 나열하지 않고 ‘딱 한 장을 바꾸고 싶다’는 포커의 경험으로 시작.
- 같은 카드의 독점, 하트 9·10을 가지고 다음 카드를 고르는 사례, BB의 기회비용을 순서대로 설명.
- R2는 카드 3장 전체 + 새 보드 5장 중 BEST 5로 갱신. R5는 6장을 2장씩 3 RUN, R6는 3인 결승.
- 발라트로 비교는 관련 절 한 곳에서 수행. 제목·모든 소제목에 경쟁작 이름을 넣지 않음. 비교의 사실 근거는 Balatro 공식 FAQ로 연결.
- 시작과 끝에 홈으로 가는 명확한 플레이 링크. 클릭을 ‘실제 게임 시작’으로 잘못 집계하지 않음.
- 본문을 서버 HTML로 제공. 클릭·로그인·실행 JavaScript가 있어야 설명을 읽는 구조를 만들지 않음.
- 제목·description·OG·Twitter 설명 일치. 내용과 일치하는 AboutPage/VideoGame JSON-LD만 제공.
- VideoGame 구조화 정보는 검색엔진의 이해를 돕는 용도다. 리뷰·가격이 없으므로 소프트웨어 앱 별점 리치 결과 자격이나 상위 노출을 주장하지 않는다. FAQ 리치 결과를 게임 사이트의 성장 수단으로 약속하지 않는다.
- CSS로 표현한 설명용 카드 2장만 사용. 새 이미지나 QA 스크린샷 파일을 저장하지 않음. 예시를 실제 경기 캡처라고 부르지 않음.
- 게임 규칙·경제·로그인/랭킹 토글·메인 화면 디자인·analytics 계정 설정은 변경하지 않음.

## 6. 실행 순서와 완료 기준

### P0 — 색인 경로와 릴리스 (배포 승인 후)

1. /about 내용·표현을 제작자가 검토한다. 재미와 게임의 의도가 맞는지가 먼저다.
2. develop의 HOME-GATE-001 등 미배포 변경을 포함할지, 소개 관련 변경만 배포할지 확정한다. main을 임의로 덮어쓰지 않는다.
3. 테스트·타입·빌드·PC/모바일 화면 확인 후 승인된 대상만 배포한다.
4. 운영 /about 본문, canonical, robots, sitemap, http/www 리디렉션을 확인한다. URL 검사에서 Google 선택 canonical과 실제 렌더링을 확인한다.
5. 실제 변경된 /about을 한 번 재수집 요청한다. 같은 요청을 매일 반복하거나 ‘수정 결과 확인’을 원인 해결 없이 누르지 않는다.
6. /ranking 제외는 HOME-GATE 릴리스에 포함될 때만 운영 사이트맵에 반영한다. 정상 리디렉션 1개를 없애기 위해 www 통합을 해제하지 않는다.
7. 수집이 계속 지연되면 호스트 크롤링 상태·서버 5xx/429·방화벽 검증봇 접근·내부 링크를 조사한다. 한글 문체 때문이라고 대체 설명하지 않는다.

완료 증거: 운영 콘텐츠 일치 + 기술적 접근 확인 + 요청 접수. **별도 후속 증거**: Search Console의 실제 최근 크롤링 시각·색인·선택 canonical. 요청만으로 DONE(색인 완료) 처리하지 않는다.

### P1 — 소개를 넘어 보여줄 근거 (1~2주 작업 계획)

- 제작자 검토 후 실제 한 판의 선택을 설명하는 짧은 기록 1개를 준비한다. 예: ‘하트가 안 보일 때 플러시를 포기한 이유’. 실제 경기의 카드·선택·결과를 쓰며 승률이나 결과를 꾸미지 않는다.
- 시작→카드 구매→쇼다운의 실제 플레이 영상/캡처는 사용자가 제공하거나 저장을 별도 승인할 때만 제작·최적화한다. 현재 AI 일러스트를 실제 게임 화면처럼 게시하지 않는다.
- 본문을 바탕으로 개발자 소개·연락처를 공개할지 확인한다. 실명·경력·상표 관계를 임의 작성하지 않는다.
- Steam/Discord의 공식 공개 링크가 준비되어 있으면 확인 후 추가한다. ‘출시 예정 플랫폼’과 현재 가능한 웹 플레이를 구분한다.
- 포커·인디게임·덱빌딩 커뮤니티에 제작자임을 밝힌 소개를 제안한다. 회원 규칙·공개 게시 승인 후 사용자 관점의 데모와 차이를 소개한다. 동일 댓글 대량 배포나 백링크 구매는 하지 않는다.

### P2 — 수요가 확인된 주제를 확장 (3~8주 관찰 계획)

- 검색어에 실제 노출이 생긴 주제부터 확장한다. 비슷한 키워드마다 내용이 거의 같은 URL을 만들지 않는다.
- 초보자에게 필요한 포커 족보/공유 덱/자원 선택 중 하나를 실제 플레이 근거로 설명한다. 다른 사이트의 포커 규칙 요약만 복제하지 않는다.
- 발라트로 비교가 실제 유입을 만들고 추가 질문도 확인된 경우, 별도 비교 글의 필요성을 검토한다. 현재는 /about 내 비교 절이면 충분하다.
- 영어 전용 URL을 만들 필요가 확인되면 실제 영어 본문·self-canonical·상호 hreflang을 함께 설계한다. locale 값만 바꾸거나 같은 한국어 문서를 영어 URL로 복제하지 않는다.

## 7. Organic Traffic 측정 설계

Search Console은 ‘검색 노출→클릭’, 분석 도구는 ‘도착→플레이’ 확인용이다. 두 도구의 수치가 같을 것이라고 가정하지 않는다.

| 단계 | 지표 | 관찰 방법 |
| --- | --- | --- |
| 발견·색인 | /about 수집 시각·색인 상태·선택 canonical | URL 검사. 주간 확인은 계획이며 자동 모니터는 아직 생성하지 않음 |
| 비브랜드 관련성 | 주제별 노출·클릭·쿼리별 평균 순위 | 웹·동일 국가/기기·최근 28일을 이전 28일과 비교. 브랜드 쿼리 분리 |
| 결과의 전달력 | 같은 쿼리·페이지·기기·순위대의 CTR | 적은 노출에서 % 변화만으로 성공을 선언하지 않음 |
| 도착 | Organic Search 세션, landing page=/ 또는 /about | GA4 실시간/DebugView로 수집 확인 후 보고. 봇·제작자·QA 접근과 구분 |
| 플레이 | play_cta_click, game_start, round_1_complete, game_complete | 기존 src/analytics/events.ts 이벤트 재사용. 새 페이지의 이동 클릭과 game_start는 별개 |

현재 /about 소스 자체에는 GA4 gtag가 없다. 운영에 Cloudflare 측정 코드가 추가되어도 GA4와 같지 않다. **소개로 들어온 자연 유입과 홈 이동의 출처가 GA4에 연결되는지 별도 검증이 필요하다.** 측정 없이 /about의 Organic 세션이 증가했다고 주장하지 않는다.

다음 측정 구현은 제안/승인 후 작업이다: 기존 동의·개인정보 정책·측정 ID를 확인해 /about에도 같은 사이트 측정을 연결하고, 소개→홈 이동을 from_about 같은 비개인정보 이벤트로 측정. URL에 내부 UTM을 붙여 원래 유입 소스를 덮어쓰지 않음. Search Console과 GA4 연결은 권한 확인 후 사용자 승인하에 진행한다.

목표:

- 먼저 /about의 실제 수집과 색인 여부를 확인한다.
- 다음으로 브랜드 외 관련 검색어가 노출되기 시작하는지 본다. 검색어 생략/익명화가 있으므로 ‘표에 없음=0명’으로 계산하지 않는다.
- 유효한 자연 유입이 플레이 시작·R1 완료로 이어지는지 확인한다.
- 현 표본 67노출·3클릭으로 월 방문자 수나 몇 % 성장을 예측하지 않는다. 28일 데이터와 검증된 전환을 쌓은 뒤 기준선·현실적인 목표를 확정한다.

색인 안 됨 → 수집·canonical·접근 문제 조사. 색인 됨+노출 적음 → 수요·설명·외부 발견 경로 검토. 노출 있음+클릭 낮음 → 동일 순위 조건의 제목/설명/의도 확인. 클릭 있음+플레이 적음 → 잘못된 장르 기대·첫 화면·게임 진입 UX 확인.

## 8. 하지 않을 것

- 경쟁작명·장르명을 모든 제목과 문단에 반복하거나 화면 밖 텍스트로 숨기기.
- 검색봇에만 다른 본문 제공, 키워드별로 복제한 doorway 페이지 양산.
- 가짜 별점·수상·평론·Steam 출시 상태·검색량·유입 전망 작성.
- /about의 설명이 /와 다른데 메인 노출을 강제하려고 canonical을 /로 바꾸기.
- 200 응답·IndexNow 접수·‘색인 가능’을 ‘구글 노출 완료’로 표현.
- 페이지가 아직 크롤링되지 않았는데 AI 문체·코어 웹 바이탈·도메인 제재를 원인으로 확정.
- IndexNow가 Google의 일반 웹페이지 색인 API라고 설명하기. Google에는 Search Console/표준 사이트맵을 사용한다.

## 9. 필요한 사용자 참여와 승인

1. 소개문과 발라트로 비교가 의도한 재미를 제대로 표현하는지 검토.
2. Search Console 브라우저 연결은 재연결되어 개요·세부 페이지·28일 실적을 확인했다. 비밀번호/새 토큰은 필요 없었다. 추가 권한이 필요해지면 별도 요청한다.
3. 실제 플레이 미디어의 공개/파일 저장 승인 또는 사용자 제공. 현재 QA 이미지 파일은 만들지 않는다.
4. 공식 Steam·Discord 링크, 제작자 공개 정보가 있다면 확인 가능한 자료 제공. 없어도 이번 소개문 게시 준비는 가능하다.
5. 2026-10-27 사용자가 이번 변경의 커밋·푸시 및 main 반영을 승인했다. 수동 운영 배포, 이후 수집 요청, 측정 추가와 외부 커뮤니티 게시 여부는 별도 범위로 유지한다.

## 10. 이번 변경의 검증

- Workers 검색 라우트 테스트 9개 통과. 공개 응답·메타데이터·현행 라운드 설명·구조화 데이터·목차 링크를 검증했다.
- 변경 파일 ESLint, 클라이언트/Worker 타입 검사, 프로덕션 빌드, CSS 순서 검사, git diff --check 통과.
- 2026-10-27 최신 원격 0554243 통합 후 검색 9개·계정 공개 게이트 4개(합계 13개), 변경 파일 ESLint, 타입·빌드·CSS 순서 검사를 재검증했다. 테스트 종료 때 Vite 정리 지연 경고가 있었지만 테스트와 후속 명령은 모두 성공 종료했다.
- Chrome에서 360×780, 402×874, 1440×900 화면을 확인했다. 가로 넘침과 끊어진 목차 링크가 없었으며 임시 viewport 설정은 복원했다. 실제 모바일 기기 검증은 아니다.
- QA 이미지는 파일로 저장하지 않았다. 게임 규칙·메인 화면·운영 데이터는 변경하지 않았다.
- 최초 검토용 로컬 미리보기: http://127.0.0.1:5189/about. 2026-10-26 검증 시점에는 운영 게시·커밋·푸시·색인 생성 요청을 실행하지 않았다. 2026-10-27 main 반영은 새 사용자 지시에 따라 진행하며, 수동 운영 배포와 색인 생성 요청은 실행하지 않는다.
