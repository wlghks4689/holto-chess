# 멀티플레이 출시 전 UI·UX 실게임 감사

작성: 2026-09-24 / Codex / 상태: 조사 완료, 주요 수정안 검토 필요

## 결론

**현재 버전을 “스포일러와 플레이어 간 표시 차이가 없는 출시 준비 완료 상태”로 판단하지 않는다.** 정상 회선의 같은 경기 공개 타이밍은 대체로 잘 맞지만, 일반 메뉴만 이용해 파이널 결과를 먼저 확인하는 경로가 실제로 존재한다. 모바일 상점의 제한시간 은폐도 출시 전 수정 우선순위가 높다. 경기 엔진의 결과 불일치나 서버 전체 정지는 이번 표본에서는 발견하지 않았다.

이번 권한 범위는 실제 멀티플레이 점검·보고와 최저 중요도 문제의 직접 수정이다. 주요 동작·규칙·경제·공개 정책은 바꾸지 않았다. 작은 표시 오류 두 건은 로컬 소스에서 수정·검증했다. **운영 배포, push, 다른 작업의 통합은 하지 않았다.**

- 별도 worktree 사용: `C:/Users/USER/.codex/worktrees/release-audit-latest/holto_chess`. 원래 Desktop 작업 폴더의 미커밋 변경은 보존했다.

첫 실행의 모바일 준비 버튼 자동 클릭은 장식 문자 때문에 정확한 accessible name 선택에 실패했다. 카드는 정상 구매했으며, 상점은 서버의 정상 60초 만료 경로로 진행했다. 두 번째 실행부터 실제 준비 버튼 selector로 수정했다. 이것은 테스트 도구의 제약이지 제품의 “클릭 불가” 결함으로 집계하지 않았다.

### MP-03 · P2 · 회선 지연이 공개 타이밍 차이로 그대로 남음 [실측]

- p2의 서버→클라이언트 메시지에 650ms 지연을 일정하게 넣었다. 같은 경기의 상대보다 공개 단계가 약 0.7초 늦었다. 예: R1 `1-primary-4` RESULT 전환 차이 **700ms**, R4 `4-secondary-37` REWARD **715ms**.
- 정상 수신 p1/p3/p4 사이에서 비교 가능한 78개 동일 경기·단계 그룹은 median 0ms, p95 25ms, 최대 46ms였다. 같은 PC에서 DOM 변경을 측정한 값이며 실제 화면 픽셀·모바일 회선의 보장값은 아니다.
- 원인: `src/ui/serverClock.ts`가 `serverNow - localReceiveTime`의 최댓값으로 시각을 추정한다. 지속적인 편도 지연은 서버 시계 오차처럼 반영되며 왕복시간 보정은 없다.
- 권고: 시계 보정 프로토콜과 지연 허용 범위를 명시한다. 시각 오차 추정·불확실성 측정·복귀 시 재동기화를 검토한다. 편도 비대칭 회선에서 절대 동시성을 보장할 수 있다고 주장하면 안 된다.
- 상태: 결과 계산이 달랐다는 뜻은 아니다. 화면을 함께 보는 사용자는 한쪽의 리버·승자를 먼저 알 수 있다.

### MP-04 · P2 · 탈락자의 전체 테이블 일정 때문에 생존자 대기가 길어짐 [실측+서버 일정]

### MP-07 · P2 · 아직 연출하지 않은 카드·승패를 클라이언트가 먼저 받음 [실측 데이터+코드]

### RISK-01 · 배포 후 구형 탭의 presentation version 불일치 [코드상 위험, 미재현]

서버는 `PRESENTATION_VERSION = 8`을 전달하지만 클라이언트는 받은 version을 검사하지 않고 번들에 내장된 timeline으로 프레임을 계산한다. 구형 탭과 신형 서버의 duration/phase 정의가 다르면 같은 startsAt에서도 다른 화면을 낼 수 있다. 이번에는 운영 중 배포하거나 구형 번들을 강제 주입하지 않았으므로 실제 발생 건수·오차를 주장하지 않는다. 출시 운영 점검 항목으로 남긴다.

## 3. 정상 확인 및 오탐 제외

- 세 방 모두 R5까지 진행했고, 수집된 pageerror/server-error/driver-error/sample-error는 0이었다. 의도적으로 발생시킨 접속 손실은 별도 시나리오다.
- 전 라운드의 표본 화면에서 document 가로 넘침은 없었다. 긴 닉네임과 공동 순위가 프로필 좌우를 무너뜨리는 현상도 검토한 화면에서는 발견하지 않았다.
- R4 3인 프로필은 360px에서도 가로 3열, 카드 3+2줄이었다. 커뮤니티 보드 하단은 약 445px로 첫 화면에 들어왔다. [R4 표본](assets/2026-09-24/r4-three-way.png).
- R5의 최종 1ST 표식은 정상 표시됐다. FINAL_WINNER 첫 프레임 캡처에서 잠깐 비어 보인 것은 등장 애니메이션이며 COMPLETE에서 확인해 결함으로 집계하지 않았다.
- R1/R3은 같은 라운드의 2·3차 매치로 자동 전환됐고, 시네마틱 중 조작용 결과 확인/속도/skip 버튼은 없었다.
- p4 R3 새로고침→재참가 후 약 1.1초 만에 현재 RIVER로 복구했다. 첫 매치부터 다시 재생하지 않았다.
- p1 JS를 8.020초 정지시킨 동안 DOM 전환이 없었고, resume 뒤 약 42ms에 현재 COMPLETE/다음 매치 1초 카운트다운으로 복구했다. 실제 모바일 운영체제의 앱 중단과 동일하다고 주장하지 않는다.
- UI를 숨기는 gate가 점수판·로그를 연출 뒤로 미루는 기본 동작은 정상이다. MP-01처럼 gate 밖의 기록 저장 경로를 별도로 막아야 한다.
- 라운드 결과의 순간적인 기존 순서/새 순위 혼합은 순위 이동 애니메이션으로 확인했으며 정렬 오류로 집계하지 않았다.

## 4. 직접 처리한 최저 중요도 변경

1. R2·R4 결과 제목이 방 전체 테이블 배열 번호를 MATCH 번호로 쓰던 오류를 수정했다. R2/R4 1차전은 MATCH 1, R4 2차전은 MATCH 2. 매칭 로딩과 결과 화면에 같은 함수를 사용한다. R1/R3 matchday, 경기 결과/페어링/서버 일정은 바꾸지 않았다.
2. 서버 공통 시작 시각 직전의 대기 문구를 “쇼다운을 준비하고 있습니다.”로 분리했다. 자기 경기를 마친 뒤에는 기존 “다른 매치 결과를 기다리는 중입니다.”를 유지한다.

검증: 전체 테스트 414개 통과 후 서버 조기 READY 거절 회귀 1개를 추가하고 해당 파일 7개 통과. 따라서 현재 고유 테스트 415개는 전체 실행 414개+신규 집중 실행으로 검증했다. Workers 12개, lint, production build 통과. 새 게임 규칙·포인트·BB·타이밍 상수 변경은 없다.

## 5. 개선 계획: 영향 범위와 원인을 함께 보는 출시 권고

이번 판단은 화면별 현상만 세는 방식이 아니라 **사용자 역할·시간·기기라는 다차원 분석**과 **서버·저장소·연출·공통 UI의 의존 관계를 나누는 복잡성 분석**을 함께 사용했다. 점검 결과 정상 회선에서의 시계·공통 종료 장치는 상당 부분 작동하지만, 그 장치가 앱의 모든 공개 경로를 통제하지는 않는다. 같은 화면의 상대방끼리는 잘 맞아도, 다른 탭의 기록이나 관전자의 별도 일정은 전혀 다른 시간 기준을 사용할 수 있다. 따라서 “싱글에서 정상” 또는 “한 탭에서 스포일러가 안 보임”만으로 멀티플레이 전체 공개 정책을 확인할 수 없다.

원인 계층을 구분하는 것이 중요하다. MP-02는 응답 데이터가 없는 문제가 아니라 CSS가 필수 상태를 제거하는 문제다. 여기에 서버 타이머를 늘리는 조치는 원인을 해결하지 못한다. MP-03은 연출 길이 자체보다 시계 추정의 지연 편향 문제라서 모든 플레이어에게 같은 대기시간을 더하는 것만으로 같은 화면을 보장할 수 없다. MP-04는 느린 클라이언트가 아니라 관전자에게 부여한 직렬 일정이 참가자의 공통 종료에 영향을 주는 구조다. 이런 문제를 하나의 “로딩이 느리다”로 묶으면 서로 다른 원인을 놓치고 정상적인 긴 타이브레이크까지 줄일 위험이 있다.

공개 시점도 단일 개념이 아니다. 서버에서 결과가 확정되는 시점, 전송되는 시점, 카드가 뒤집히는 시점, 최종 순위표가 열리는 시점, 과거 기록으로 저장되는 시점이 현재 분리되어 있다. 그 자체는 정상적인 설계가 될 수 있지만, 각 경계의 허용 범위가 명시되어야 한다. 현재 구현은 미리 결과를 보내 매끄럽게 재생하는 장점과 클라이언트가 미래 정보를 갖는 한계를 동시에 갖는다. 이번 감사는 그 한계를 부정행위 확정으로 과장하지 않고, 실제 일반 사용자 동선에서 열리는 기록 스포일러와 기술적 데이터 열람 경로를 나눠 보고했다. 공개 정책을 먼저 정하면 이후 수정도 과도하게 커지지 않는다.

사용자 역할의 분리 역시 필수다. 탈락자에게 생존자의 화면을 제공하는 기능은 유용하지만, 화면 정렬의 기준과 실제 사용자 정체성까지 바꾸면 YOU가 잘못 붙는다. 같은 이유로 연결 상태는 특정 경기 내용과 별개의 정보다. 시네마틱이 콘텐츠를 숨길 수는 있어도 네트워크 상태나 “관전 중”이라는 맥락까지 가려서는 안 된다. 작고 항상 보이는 상태 레이어는 결과 스포일러를 추가하지 않으면서 복구 가능성과 신뢰를 높일 수 있다.

마지막으로 이번 수치는 표본의 증거이지 완벽성의 증명은 아니다. 독립 사용자 8명 완주와 지연·정지 실험은 한 클라이언트 검사보다 강하지만, 같은 PC의 headless Chrome은 저사양 Android의 렌더링 지연, iOS 앱 중단, 대륙 간 비대칭 회선, 수백 방 동시 접속을 대신하지 못한다. 관측된 불량은 고쳐야 하고 관측되지 않은 조건은 별도의 출시 체크로 남겨야 한다. 이 구분 없이 “문제없음”으로 마무리하면 출시 직후 재현하기 어려운 체감 오류를 남길 수 있다.

아래 10개는 승인 없이 규칙을 바꾸기 위한 아이디어가 아니라, 확인된 원인에 대응하는 실행 제안과 완료 기준이다.

1. **공개 완료를 한 번만 정의하는 상태 모델.** GAME_RESULT 도착을 곧 사용자 공개 완료로 간주하지 말고, presentation의 공통 종료를 통과한 결과만 기록/공유/재대전 화면에 올린다. 구현 시 현재 탭의 React state만 보는 대신 저장된 기록에도 공개 조건을 남겨 다중 탭이 같은 기준으로 판단하게 한다. 완료 기준은 연출 중 새 탭, 새로고침, 이전 기록 목록 진입을 반복해도 이번 결과가 보이지 않고 공개 후에만 정상적으로 한 건 저장되는 것이다.

2. **모바일 온라인 필수 정보 영역.** 화면 폭이 줄어들 때 장식·보조 설명부터 줄이고, 제한시간·내 준비 여부·대기 인원·카드 부족 경고는 남긴다. 상점 버튼 위에 짧은 한 줄 또는 작은 두 줄로 통합하면 기존 중앙 카드 구성도 유지할 수 있다. 준비 후에는 같은 자리에 취소/대기 상태를 표시해 버튼 상태가 바뀐 이유를 설명한다. 완료 기준은 360×660부터 PC까지 모든 상점에서 제한시간과 준비 상태가 보이고 카드·버튼을 가리지 않는 것이다.

3. **시계 정확도에 대한 예산과 계측.** 단순한 “동기화됨” 대신 추정 offset, 최근 RTT, jitter, 마지막 보정 시각을 개발 진단 값으로 남긴다. RTT 기반 보정은 비대칭 지연을 완전히 해결하지 못하므로 허용 가능한 화면 차이와 재동기화 조건을 함께 정한다. 사용자를 계속 멈추게 하는 방식보다 서버 공개 시점과 클라이언트 따라잡기를 일관되게 만드는 편이 낫다. 완료 기준은 0/150/650ms 지연과 jitter별 p95·최대 공개 차이를 자동 리포트하고 역행 재생이 없는 것이다.

4. **matchId 중심 관전 일정.** 참가자마다 몇 번째 항목인지를 기준으로 슬롯을 맞추기보다 같은 경기의 공개 기준 시각을 중심에 둔다. 관전자는 이미 진행 중인 경기의 현재 위치에 합류하고, 다음 관전 대상을 고르더라도 참가자 공통 종료를 연장하지 않는다. 긴 승부가 실제 존재할 때의 참가자 대기와, 관전자만 더 보기 위한 재생 시간을 구분해야 한다. 완료 기준은 탈락자 0/1/4명이 연결한 경우 동일한 실제 경기 집합의 참가자 진행 시간이 바뀌지 않는 것이다.

5. **시네마틱 외부의 연결 상태 레이어.** 게임 내용과 별개로 작은 연결 표시·재접속 안내를 유지한다. 재연결 중에는 클릭 가능한 행동을 안전하게 잠그되 이미 받은 카드 연출을 유지할지 여부를 일관되게 정한다. 수동 재시도가 자동 재시도와 충돌하거나 여러 소켓을 만들지 않는지도 확인한다. 완료 기준은 매치 시작, 리버, 결과 대기 각각에서 끊어도 현재 연결 상태를 사용자가 알 수 있고 복구 후 같은 좌석·현재 단계로 돌아오는 것이다.

6. **관전자 신원과 시점의 명시적 분리.** viewerId 하나에 실제 좌석과 보고 있는 좌석 의미를 함께 담지 말고, 실제 사용자 ID와 관전 대상 ID를 별도로 전달한다. 관전자가 왼쪽에서 보고 있는 카드가 누구 것인지 명시하고 YOU 표식을 제거하거나 실제 본인에게만 남긴다. 표시만 바꾸고 구매 권한 검사는 여전히 실제 사용자로 유지해야 한다. 완료 기준은 탈락 직후, R4 다음 경기, R5에서 “관전 중 · 이름”이 지속되고 관전 대상 변경이 결과 공개를 앞당기지 않는 것이다.

7. **서버 공개 데이터 경계의 제품 결정.** 일괄 전송은 매끄러운 재생과 연결 복구에 유리하지만 미래 결과를 클라이언트에 맡긴다. 일반 UI 스포일러 차단만 목표라면 이 한계를 명시하고 기록/로그 경로를 닫는다. 기술적 열람까지 막으려면 현재 공개된 street까지만 projection하고 다음 reveal을 서버 이벤트로 전달하는 안을 비교한다. 완료 기준은 선택한 위협 모델에 맞는 테스트가 존재하고, 공개 전 메시지의 허용 필드와 금지 필드를 문서로 설명할 수 있는 것이다.

8. **짧은 화면 높이에 맞춘 R2 결과 구성.** 폭만 기준으로 줄이지 말고 높이 제약도 확인한다. 이전 RUN의 보드 전체 대신 이미 사용 중인 간결한 승부 카드 요약을 더 낮게 배치하고, 상단 헤더·패널 여백을 줄여 RUN2 보드와 보상 핵심이 동시에 보이도록 한다. 카드 글자를 무작정 줄이는 접근은 피한다. 완료 기준은 360×660의 실제 viewport 스크린샷에서 카드 값·RUN 구분·현재 결과가 스크롤 없이 식별되고 PC 배치는 유지되는 것이다.

9. **구형 클라이언트와 서버 타임라인 호환성.** 버전 필드를 단순 참고값으로 보내는 데서 끝내지 말고 지원 범위를 검사한다. 경기 도중 강제 새로고침은 또 다른 불편이므로, 입장 전 업데이트 안내 또는 호환 타임라인 유지 중 어느 정책을 쓸지 정한다. 이미 시작한 방에 영향을 주는 배포는 특히 별도 회귀가 필요하다. 완료 기준은 구형 탭+신형 서버 조합에서 침묵하는 오재생 대신 안전한 호환 동작이나 명확한 안내가 나오고 세션은 보존되는 것이다.

10. **재현 가능한 출시 게이트로 전환.** 이번의 실방 자동화와 스크린샷을 일회성 보고로 버리지 말고, 비운영 환경에서 고정 시드·8좌석·재접속·관전·작은 화면을 반복하는 테스트 묶음으로 만든다. 자동 지표는 화면 오버플로, 동일 matchId의 공개 차이, 결과 조기 메뉴 접근, 기록 중복을 포함한다. 실제 iOS/Android와 원거리 회선 검증은 별도 수동 체크로 연결한다. 완료 기준은 출시 후보마다 같은 보고서를 재생성하고, 실패 항목·미검증 항목을 숨기지 않고 배포 승인 전에 확인할 수 있는 것이다.

## 6. 증거·재현 도구 및 남은 범위

도구: `holto-chess/tools/multiplayer-audit.mjs`, `summarize-multiplayer-audit.mjs`.

원본 데이터는 해당 worktree의 `holto-chess/.audit/multiplayer{,-resilience,-suspension}/`에 보존했다. 각 폴더에 events.jsonl, summary.json, run.json, 스크린샷이 있다. 전체 원본은 Git에서 제외하고 핵심 증거 6장만 본 보고서 옆 assets에 보존했다. 보고서의 방 코드는 이번 테스트 방이며 사용자 세션 토큰은 없다.

재실행 예시(기본 대상은 localhost, 운영 실행은 명시적으로만):

```powershell
$env:PLAYWRIGHT_MODULE = 'C:/Users/USER/.cache/codex-runtimes/codex-primary-runtime/dependencies/node/node_modules/playwright'
$env:AUDIT_ORIGIN = 'http://localhost:5173'
$env:AUDIT_PLAYERS = '8'
```
