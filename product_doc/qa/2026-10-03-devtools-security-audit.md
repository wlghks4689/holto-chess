## 결론 및 범위

멀티플레이는 서버 권위와 플레이어별 projection이 있으며, 상대 상점 카드 ID·전체 소유권 풀·난수 seed·다른 좌석의 token을 직접 전송하는 경로는 검토 범위에서 발견하지 못했다. 미공개 커뮤니티 카드도 서버 시각에 맞춰 불투명 슬롯으로 바꾼다. 하지만 점수 스냅샷, 탈락 후 카드 배열, 연출 메타데이터에는 간접 스포일러가 남아 있다. 상점 중 상대 BB의 즉시 갱신은 구매 랭크 추론을 허용한다. 익명 입장 구조는 한 사람이 여러 좌석을 차지할 수 있고, 인증 전 연결이 정상 재접속 자원을 선점할 수 있다. 따라서 “정보 노출·치팅 문제가 없다”는 판정은 내릴 수 없다.

싱글플레이는 `src/ui/App.tsx:170`의 React 상태에 게임 전체가 있다. 상대 owned/shop 카드, ownershipCardPool, abilityDraft.deck, seed, 계산된 roundResults가 브라우저에 존재한다. 개발자도구로 열람·변조하거나 로컬 기록을 편집할 수 있다. 이는 멀티플레이 서버 권한 우회와 구분해야 한다. 현재 로컬 결과를 서버의 공식 성적에 반영하는 경로는 확인하지 못했다. 경쟁 기록으로 사용할 계획이라면 별도 서버 판정이 필요하다.

운영에는 공개 GET/HEAD만 사용했다. 실제 이용자의 방에 접속하거나 변조·부하 요청을 보내지 않았다. 취약 동작은 로컬 함수와 Cloudflare Vitest 런타임의 격리된 방에서 재현했다. 운영 HTML의 번들 경로는 `/assets/index-a6n4bQ0O.js`, `/assets/index-C8qtDekM.css`였다. Worker 배포 버전·정확한 운영 소스 SHA는 관리 API로 확인하지 않았으므로 코드 감사 결과를 운영 침투 테스트 완료로 표현하지 않는다.

## 검토 기준: 공개 시점과 권한을 함께 분해

다차원 분석에서는 시간, 역할, 저장 위치를 교차해서 확인했다. 시간은 카드 선택 전, 상점 준비 중, 전원 확정 후 매칭, 각 스트리트, RUN 결과, 라운드 결과, 최종 기록 공개로 나누었다. 서버에서 승패를 계산한 시점과 이용자가 승패를 알아도 되는 시점이 다르기 때문이다. R1/R3처럼 세 매치를 한꺼번에 계산하는 구조에서는 첫 화면에 마지막 매치 결과가 섞이지 않아야 한다. 또한 하나의 테이블만 기준으로 안전하다고 판단하면 동시에 진행되는 다른 테이블의 점수가 보조 필드를 통해 노출되는 문제를 놓칠 수 있다. 실제 이번 재현에서 기본 players.points는 0으로 가려졌으나 첫 매치의 standingsBefore에는 다른 테이블의 +3P가 들어가 있었다.

역할은 자기 좌석, 다른 생존 좌석, 탈락 관전자, 인증 전 연결, 동일 세션의 재접속으로 구분했다. 자기 상점과 자기 패는 당연히 자기 브라우저에 있어야 한다. 반면 관전자에게 다른 플레이어의 private view를 만드는 과정에서는 카드뿐 아니라 카드 개수, 구매 횟수, 시작 카드 같은 보조 필드도 확인해야 한다. 이번에는 일반 관전의 ownedCards가 hidden 슬롯으로 바뀌고 shopCards가 비워지는 방어를 확인했다. 다만 방 전체의 익명 좌석 발급 정책이 별개의 약점이다. 서로 다른 token을 발급해 주는 것만으로 서로 다른 사람임을 보장하지 못하므로, 한 사람이 정상 입장 API를 여러 번 호출하면 다른 좌석의 정보를 자기 권한으로 받을 수 있다. 이것은 다른 token을 추측해 훔치는 공격과 원인·대응이 다르다.

저장 위치는 서버 RoomSnapshot, WebSocket PlayerView, 브라우저 메모리, localStorage를 분리했다. 서버 저장소에는 전체 게임이 필요하지만 전송 객체에는 공개 가능한 항목만 있어야 한다. 클라이언트의 CSS, 뒷면 이미지, React 컴포넌트 분기, 시네마틱 gate는 이미 전송된 값을 비밀로 유지하지 못한다. 싱글플레이의 전체 상태나 자기 세션 token을 해당 사용자의 개발자도구에서 숨긴다는 목표도 달성할 수 없다. 반대로 멀티플레이에서 브라우저에 없는 미래 카드 값을 단말 시계를 조작하는 것만으로 새로 얻는 경로는 현재 서버 시각 검증이 막고 있다. 보안 판단은 화면이 아니라 실제 JSON 전송 경계와 서버의 상태 변화를 기준으로 해야 한다.

복잡성 분해에서는 정보 projection, 일정 생성, 명령 검증, 세션 발급, 연결 자원을 따로 조사했다. 이들 사이의 의존성도 확인했다. 예를 들어 탈락 처리 자체는 올바르게 카드 소유권을 반환하지만, 그 직후 빈 ownedCards를 자기 view로 보내면 alive만 감춰도 탈락을 미리 알게 된다. 인증 timeout 자체는 존재하지만 인증 전 소켓이 전체 연결 cap을 차지하면 정당한 재접속을 먼저 막을 수 있다. 따라서 기존 게임 판정이나 경제 수치를 바꾸는 대신 각 경계가 책임지는 공개 스냅샷과 자원 배분을 수정하는 것이 맞다. 점수 공개와 실제 정산을 분리하고, 새 정책이 필요한 BB·참가자 식별은 사용자 결정 대상으로 남긴다.

마지막으로 이미 공개된 모든 홀 카드와 리버를 가지고 포커 족보를 계산하는 행위는 비밀 데이터 유출과 다르다. 전체 카드가 공개된 뒤 결과 애니메이션이 끝나기 전에 승자를 계산하는 것을 JavaScript 난독화나 개발자도구 차단으로 막을 수는 없다. 보호해야 할 것은 아직 공개되지 않은 카드·다른 상점·미래 매치·정산 상태다. 반면 최신 기획과 관련 테스트가 명시한 R2 공개 드래프트, 픽 직후의 어빌리티 공개, 전원 확정 후 매칭 패 공개는 허용된 정보로 분류했다. 과거 문구만 보고 이들을 새로운 유출이라고 판단하거나 임의로 숨기지 않았다.

## 확인된 방어

- private view는 본인 owned/shop 카드만 전송하며 전체 ownershipCardPool, seed, logs, tokenHash는 allowlist에 없다.
- 다른 사람의 상점 예약 카드 BUY/LOCK, 다른 사람 소유 카드 SELL, caller-supplied playerId/stackBB, 잘못된 phase/turnKey를 거부한다. BB·가격·족보·보상은 서버가 계산한다.
- 4096자 메시지 제한, 필드 allowlist, 카드 ID/중복/어빌리티 slot/닉네임 검증, `__proto__` 명령 거부를 확인했다.
- 세션 token은 암호학적 32바이트 난수이며 서버에 hash로 저장한다. 다른 방의 token과 외부 Origin을 거부한다. 연결 인증은 URL query가 아닌 첫 메시지에서 한다.
- 저장·동시 구매·리롤을 직렬화하고 저장 성공 후 broadcast한다. 최근 requestId 64개에 대한 동일 요청 재시도는 중복 정산하지 않는다. 이는 무기한 replay 차단을 의미하지 않는다.
- 공개 전 보드 카드 값, 다음 매치의 카드 값, R5 향후 공개 배치, 최종 standings/기록을 서버 시각에 따라 제한한다. R5 하위 등수 공개 중 우승자·전체 보상이 직접 유출된다는 초기 가설은 확인되지 않아 발견 항목에서 제외했다.
- 탈락 관전용 shopCards는 비우고 ownedCards는 hidden 슬롯으로 바꾼다. 상대 어빌리티 이득 수치는 제거한다.
- 프로덕션 난수는 crypto 경로이고 클라이언트에서 seed를 지정하는 명령은 없다. production debug inspect는 DEV 조건이다.

## 후속 개선안 10개 — 제안이며 구현·승인 아님

1. **상점 경제 공개를 스냅샷으로 운영한다.** 자기 화면의 잔액과 서버의 구매 검증은 현재 값으로 유지하고 다른 좌석에는 상점 진입 시 잔액을 표시하는 방안을 검토한다. 준비 취소 뒤 추가 구매, 판매, 잠금, 할인, 무료 리롤까지 같은 공개 기준을 적용해야 한다. 구매한 카드 ID만 삭제하는 현재 방식으로는 가격 역추론을 막지 못한다. 반면 모든 BB를 숨기면 기존 전략 정보를 바꾸므로 갱신 시점과 표시 의미를 먼저 확정한다. 완료 조건은 자기 구매 후 자기 잔액이 맞고 상대 payload 차이에서 구매 랭크가 드러나지 않는 것이다.

2. **공개 점수의 원본을 한 곳에서 만든다.** points, standingsBefore, standingsAfterRuns, swissBefore, rewards의 before/after가 각각 다른 계산 시점의 원본을 참조하면 보조 필드가 필터를 우회한다. 경기별 순서를 고려한 공개 점수 projection을 두고 외부 payload가 그 값을 사용하도록 한다. 동시에 진행되는 다른 테이블의 아직 공개되지 않은 보상은 그 경기 원본에 이미 기록되어 있어도 반영하지 않는다. 다양한 pairing 순서를 가진 seed에서 모든 좌석의 첫 프레임을 비교하고 공개된 경기만 더했을 때 같은 값이 나오는지 검증한다.

3. **탈락 연출에 필요한 자기 패를 보존한다.** 경제와 카드 풀에서는 탈락 카드의 반환을 즉시 처리해도 되지만 presentation이 쓰는 정보는 정산 전 잠긴 카드 스냅샷을 참조해야 한다. alive 하나를 가리는 데서 그치지 않고 ownedCards, shopCards, selectedCardIds, handLimit, abilityStartingCard의 조합을 확인한다. 몰수패처럼 실제로 처음부터 카드가 부족했던 상황과 정상 패를 가지고 탈락한 상황도 분리해야 한다. 서로 다른 생존 결과를 가진 동일한 공개 전 입력의 자기 view가 탈락 여부만으로 달라지지 않는지를 회귀 조건으로 삼는다.

4. **결과에 따라 달라지는 일정의 선전송을 줄인다.** R5 순위 프레임 수, 추가 타이브레이크 보드 수, high-card 존재 여부, 전체 종료 시각이 경기 결과를 전달할 수 있다. 처음에는 결과와 무관한 기본 구간만 공개하고 결정 구간 도달 시 서버가 추가 일정을 선언하는 방안을 검토한다. 이때 짧은 테이블을 오래 대기시키는 문제와 재접속 클라이언트의 현재 프레임 복원도 함께 해결해야 한다. 운영 중인 타이브레이크를 삭제하거나 실제 재생을 임의로 단축해서 비밀을 맞추면 안 된다. 동률 여부만 바꾼 입력의 최초 일정도 비교해야 한다.

5. **입장 token과 사람의 신원을 구분한다.** 현재 token은 특정 좌석의 명령 권한을 충분히 증명하지만 같은 사람이 여러 token을 받는 것을 막지는 못한다. 경쟁전에는 계정 또는 검증된 플랫폼 신원에 좌석을 연결하고 방마다 한 좌석을 허용하는 방향을 검토한다. 초대 방은 방장 승인이나 일회성 입장 티켓도 선택지다. 익명 캐주얼 모드를 유지할지 경쟁 모드만 강화할지 먼저 결정해야 한다. 단순 IP 제한은 같은 네트워크에서 정상 참가하는 여러 사람과 Discord 프록시를 구분하지 못하므로 완전한 대책으로 채택하지 않는다.

6. **인증 전 연결과 재접속의 자원을 분리한다.** unauthenticated socket을 전체 cap까지 허용하지 말고 별도 작은 예산을 두며, 인증된 기존 좌석의 재접속이 우선권을 가질 수 있게 설계한다. 브라우저 WebSocket에서 사용자 지정 Authorization 헤더를 보낼 수 있다는 가정은 피한다. 필요하면 짧은 수명의 일회성 연결 티켓을 발급하는 절차를 검토하고 기존 token을 로그에 남는 URL로 이동시키지 않는다. timeout 후 cap이 실제 회복되는지, 정상 8명이 접속 중인 방에서도 재접속이 되는지 실제 runtime 테스트로 확인한다.

7. **소켓이 아니라 좌석·방에도 메시지 예산을 둔다.** 지금은 새 연결에서 카운터가 시작되므로 연결을 갈아타면 이전 소켓의 메시지 제한과 분리된다. 정상 시각 동기화와 플레이 명령을 구분해 인증된 좌석에 지속되는 예산을 검토한다. 같은 requestId의 재시도는 필요한 ACK를 돌려주되 매번 방 전체의 큰 view를 재생성·전송해야 하는지 확인한다. 한 소켓의 기준 수치를 근거 없이 줄이기보다 재접속·동시 8인·느린 회선의 정당한 재시도를 함께 측정해 방 전체의 저장·broadcast 비용을 제한하는 것이 목적이다.

8. **새 보안 회귀는 데이터의 동일성도 검사한다.** 미공개 카드 ID가 JSON에 없는지만 확인하면 숫자 점수, 배열 길이, frame 수, 종료 시각을 통한 유출을 놓친다. 공개 정보와 자기 정보가 같은 두 게임의 비밀 결과만 바꾸고 현재 시점의 전체 payload가 같은지 비교하는 테스트를 추가한다. 여러 테이블, R3 경계 탈락, R4 추가 보드, R5 공동 순위, 관전자·재접속을 포함한다. 현재 74개 관련 테스트가 통과하면서도 이번 누락이 재현된 이유가 여기에 있다. 타입 allowlist 변경 시 이러한 검증을 함께 갱신한다.

9. **브라우저 보강과 세션 수명은 노출 경계와 함께 다룬다.** CSP와 MIME·referrer 정책을 실제 필요한 이미지·오디오·Analytics·Discord 자원에 맞춰 검토한다. 먼저 보고 전용으로 깨지는 정상 요청을 확인하고 최종 강제 정책을 적용하는 방법도 있다. localStorage에 있는 자기 token을 사용자에게서 숨길 수는 없으므로 인증 탈취 위협은 XSS 예방·세션 만료·폐기·재접속 검증으로 줄여야 한다. 이미 안전한 무토큰 query 원칙과 서버 hash 저장은 유지한다. 보강 헤더가 현재 발견한 점수·BB 유출까지 해결한다고 표현하지 않는다.

10. **싱글 결과를 경쟁 성적과 분리하고 검증 근거를 운영에 연결한다.** 현재 싱글은 로컬 체험 구조로 설명하고, 향후 공식 순위·보상을 연결한다면 서버가 진행·난수·명령·결과를 판정하는 범위부터 정한다. 클라이언트가 저장한 승점이나 replay JSON만 신뢰해서는 안 된다. 이번 코드 감사에서 확인된 각 누락을 수정한 뒤 배포 SHA, 실제 WebSocket 프레임, 공개 전/후 상태, 정상 플레이 완주 결과를 연결해 기록한다. 운영에서 큰 부하를 발생시키기 전에 격리 환경에서 연결 점유와 메시지 폭주를 검증하고 확인하지 못한 항목은 계속 미검증으로 남긴다.

외부 검토 기준: [OWASP WebSocket Security](https://cheatsheetseries.owasp.org/cheatsheets/WebSocket_Security_Cheat_Sheet.html)의 메시지별 권한 검증·입력 검증·연결/자원 제한과 [Cloudflare Durable Object State](https://developers.cloudflare.com/durable-objects/api/state/)의 동시 실행 경계를 참조했다. 제품별 발견 사항과 우선순위는 위 저장소 코드 및 로컬 재현에서 판단했다.
