관측 중에는 코드 수정·운영 배포·경기 상태 조작을 하지 않았다. 경기 종료 후 최종 로그를 저장하고 실시간 수집기를 종료했다.

## 사용자 승인 후 조치 및 검증

사용자가 경기 종료 후 원인에 대한 조치 설명과 작업 진행을 요청했다. 플랫폼의 최초 알람 지연 원인을 추측해 바꾸지 않고, 확인된 애플리케이션 결함인 '만료된 예약을 기다리는 동안 인증된 동기화도 게임 진행을 복구하지 못함'을 수정했다.

- `GameRoom.recoverOverdueBarrier`: 인증·방·좌석·만료 검사가 끝난 SYNC_CLOCK 처리에서 서버 시각으로 기존 barrierDeadline을 확인하고 기존 forceBarrier를 최대 한 번 호출한다. 영속 저장 후 모든 좌석에 공개 가능한 뷰를 방송하고 다음 알람을 예약한다.
- 단순 시계 응답에서는 기존 overdue alarm 보존 규칙을 유지한다. 복구 후 전체 방송까지 수행했을 때만 오래된 예약 교체를 허용한다.
- `roomConnection`: 서버가 공개한 마감시각을 서버 시계 추정값으로 비교한다. 1초의 유예 후 기존 1초 체크 주기에서 재확인한다. 재요청 간격은 최소 2초이며, 정상 상태는 기존 10초 주기를 유지한다. 숨긴 탭에서는 요청하지 않는다. 브라우저가 단계나 카드 공개를 만들지 않는다.
- 재접속/백그라운드/네트워크 단절 시에는 기존 전송 복구 경로를 유지한다. 이 수정은 연결된 활성 탭의 확인 요청으로 지연 알람을 보완한다. 모든 탭이 닫혀 있으면 기존 서버 알람이 진행을 담당한다.
- 운영 진단 로그에 `barrier.recovered`와 마감시각·초과시간·이전 단계/리비전을 추가했다.

검증 결과:

1. 실제 로컬 Cloudflare Durable Object에 알람 배달이 없는 상태를 주입한 테스트: 수정 전 DRAFT_ORDER 잔류 실패를 확인했고 수정 후 통과했다.
2. 두 클라이언트 전체 방송, 저장 실패 시 이전 상태 유지, 중복 동기화·늦은 알람에 대한 단일 전환, 공개 중 조기 전환 금지 검증 통과.
3. R6 준비시간 종료 전 복구 불가, 종료 후 새 공개 시작시각 확보, 이후 모든 공개 단계와 COMPLETE 도달 검증 통과.
4. 전송 테스트 22개 통과. 서버 테스트 총 27개 통과: deadlineRecovery 2, disclosureScheduling 5, serverDiagnostics 5, room 15. 첫 병렬 실행의 기존 room 생성 rate limit 테스트는 201/429 불일치로 실패했으나 room 파일 단독 재실행에서는 15개 모두 통과했다. 관련 제한 코드는 수정하지 않았다.
5. TypeScript 앱/Worker, 변경 파일 ESLint, 프로덕션 빌드, diff 공백 검사 통과. 기존 로컬 secrets 미설정·큰 chunk 경고는 남아 있다.
6. 실제 브라우저의 전송 코드 + 모의 알람 지연 환경: PC 1440×900에서 DRAFT_ORDER → OPEN_DRAFT 4,002ms, 모바일 393×852에서 4,013ms. 기준 마감 3,000ms, 브라우저 오류 0. 이 결과는 운영 네트워크의 최악 지연 상한이 아니다. 실제 서버 메서드는 위 Durable Object 테스트로 별도 검증했다.

공식 문서도 setAlarm 실행은 유지보수·장애 조치 시 최대 1분 지연될 수 있다고 설명한다: [Cloudflare alarm storage methods](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/#alarms). 이번 운영 지연이 해당 내부 사건 때문인지는 확인할 수 없다. 따라서 알람을 정밀한 유일 전환 신호로 가정하지 않는 복구 경로를 추가했다.

현재 로컬 수정·검증 완료. 커밋·push·운영 배포는 하지 않았다. 실제 운영 멀티플레이에서 수정 후 검증은 배포 이후 남아 있다.
