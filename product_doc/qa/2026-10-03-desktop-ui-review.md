# 포레나 PC 화면 배치 검토

> 후속 상태: 아래 최초 검토는 당시 재현 기록으로 보존한다. 같은 날 사용자의 전체 수정 승인 후 8개 항목을 수정했다. 구현·검증 결과와 남은 한계는 문서 마지막의 **후속 수정 및 검증**에 기록했다. 커밋·push·배포는 하지 않았다.

2026년 10월 3일 한국 시간에 최신 main을 대상으로 검토했다. PC에서도 카드 줄바꿈과 화면 높이 초과가 재현된다. 특히 R5 매칭 카드의 줄 수가 창 높이에 따라 역전되는 문제, 쇼다운 진행 버튼의 화면 이탈, 순위표 하단 버튼의 행 가림을 우선 수정할 필요가 있다. 이번 요청은 검토이므로 게임 코드와 규칙은 변경하지 않았다.

## 기준 코드와 검증 범위

- `main`: `39ba4db`에서 `cd8aee4cfb59ded774608807911b8698587617e8`까지 `git pull --ff-only origin main` 완료.
- 기존 미추적 `.wrangler-config/`, `varco-export/`, `2026-10-02-crazygames-upload-handoff.md`는 보존했다. 커밋, push, 배포는 하지 않았다.
- 기본 Workers 개발 서버는 로컬 Wrangler 로그와 registry 파일 권한 오류로 기동하지 못했다. 기존 `dev:local` 설정으로 React 개발 서버를 5173 포트에 기동했다. 따라서 이번 결과는 최신 로컬 UI에 대한 것이며 운영 배포 상태 검증이 아니다.
- 기존 `/responsive-preview`에서 실제 UI 컴포넌트를 사용하는 33개 상태를 1280×720, 1366×768, 1440×900, 1920×1080, 1024×900에서 검사했다. 추가 800×900, 960×900, 960×720, 1024×768의 8개 상태를 검사했다. 총 197개 상태와 뷰포트 조합의 DOM 치수를 관측했다.
- 실제 싱글 플레이에서도 시작 메뉴, 설정, 어빌리티 공개와 확대 창, 카드 구매, R1 매치 3회, R1 순위표, R2 공개 드래프트까지 UI를 통해 진행했다.
- 사용 언어는 한국어다. CSS 픽셀 기준이며 OS 배율, 다른 브라우저 엔진, Discord 및 CrazyGames iframe의 실사용 배치는 이번 검사 범위 밖이다.

### 검증용 화면의 한계

검증 데이터는 긴 닉네임, 큰 BB와 점수, 최대 카드 수를 포함한다. 외곽 헤더와 준비 버튼은 검증용 래퍼이며 실제 싱글 화면과 완전히 같지 않다. 따라서 검증용 페이지의 문서 높이를 실플레이의 정확한 높이라고 해석하면 안 된다. 실플레이로 확인한 값은 아래에 별도로 표시했다.

`results-r5` 같은 합성 상태도 매트릭스에 포함되어 있지만 실제 게임의 R5는 최종 결과 경로를 사용한다. 해당 합성 라운드 순위표의 줄바꿈은 실제 R5 장애로 보고하지 않았다. 카드의 발광과 등장 효과에 따른 일시적인 좌표 차이, 의도된 장식의 패널 초과도 카드 줄바꿈이나 실제 콘텐츠 가림으로 집계하지 않았다.

## 확인한 문제

### 1 R5 매칭 프로필의 카드가 창 높이에 따라 두 줄로 바뀜

**우선순위 P1. 검증용 화면에서 시각적으로 재현.**

`match-r5-7`의 네 프로필 모두 960×900에서 6장과 1장, 800×900에서 5장과 2장으로 나뉜다. 같은 960px 너비에서 높이를 720px로 줄이면 7장이 한 줄이 된다. 1440×900과 1920×1080의 넓은 PC 화면에서는 한 줄이었다. 즉 PC 전체가 항상 깨지는 문제가 아니라 특정 창 크기의 조건 누락이다.

원인은 `responsive.css:44`의 기본 `flex-wrap:wrap`, `responsive.css:45`의 고정 53px 카드 폭과 6px 간격, `responsive.css:474`에서 시작하는 **높이 800px 이하 전용** 7열 규칙의 조합이다. 960×900에서 카드 영역은 약 399px인데 7장의 필요 폭은 407px이다. 높이가 800px를 넘으면 폭을 나눠 쓰는 7열 규칙이 사라져 마지막 카드만 내려간다. `showdown-prep.css:32`에도 최종 매칭의 wrap 선언이 있다.

이는 커뮤니티 카드와 크기를 같게 유지해야 해서 생기는 필연적인 제약이 아니다. 이미 최종 쇼다운은 `responsive.css:36`에서 7열 가변 폭을 사용한다. 매칭 프로필에도 같은 한 줄 배치 원칙을 적용하되 실제 컨테이너 폭으로 카드 크기를 결정하는 것이 적절하다.

재현: `/responsive-preview?case=match-r5-7`.

### 2 쇼다운의 다음 매치 버튼이 노트북 화면 밖으로 내려감

**우선순위 P1. 실제 싱글 플레이에서 재현.**

1280×720의 실제 R1 첫 매치 결과에서 문서 높이는 859px, 다음 매치 버튼의 세로 범위는 760∼810px이었다. 커뮤니티 카드는 632∼712px에 있어 간신히 보이지만 진행 버튼은 스크롤 전에는 전혀 보이지 않았다. 가로 공간은 충분한데 프로필 박스 내부 간격과 상하 여백이 큰 상태다.

검증용 화면에서도 1366×768의 R1은 문서 높이 815px, R3는 846px이었다. R2 RUN 1 결과는 1280×720에서 문서 높이 974px이며 다음 RUN의 보드가 820∼911px에 놓인다. 자동 진행 중인 보드를 보기 위해 스크롤해야 한다는 점에서 단순히 아래 여백이 남는 문제보다 우선순위가 높다.

관련 선언은 `cinematic.css:1`의 외곽 margin과 padding, `cinematic.css:117`의 프로필 패딩, `cinematic.css:139`의 보드 패딩, `cinematic.css:172`의 족보 영역, `cinematic.css:241`의 footer 간격이다. `responsive.css:487`의 낮은 PC 높이 보정은 R4에 한정되어 R1∼R3의 전체 높이를 해결하지 못한다.

재현: 실제 싱글 R1 결과 또는 `/responsive-preview?case=showdown-r2-run1-result`.

### 3 라운드 순위표 진행 버튼이 순위 행을 덮음

**우선순위 P1. 실제 싱글 플레이에서 재현.**

1280×720의 실제 R1 순위표는 문서 높이가 1008px이었다. 화면을 맨 위로 올리면 6위 행은 y=632∼688px인데, 라운드 마감 버튼을 담은 바가 y=634∼706px에 겹친다. 7위와 8위는 더 아래에 있어 추가 스크롤이 필요하다. 진행 버튼을 볼 수 있다는 이유만으로 순위표가 한 화면에 맞는 상태는 아니다.

`styles.css:130`의 `position:sticky; bottom:14px; z-index:20` 바가 아래 콘텐츠 위에 떠 있으며, 폭이 좁을 때만 적용되는 static 배치가 PC에는 적용되지 않는다. 동시에 라운드 제목, 순위표 헤더, 56px 행 8개, 히스토리와 하단 바의 총 높이를 함께 제한하지 않는다. `styles.css:303` 부근의 표 행 높이와 `styles.css:352`의 모바일 전용 보정도 관련된다.

이 문제는 점수나 닉네임을 짧게 바꾸어도 없어지지 않는다. 실제 AI 기본 닉네임과 정상적인 점수로도 재현했다.

### 4 R4 드래프트에서 아래 카드와 내 핸드를 동시에 볼 수 없음

**우선순위 P1. R4는 검증용 화면에서 재현했고 R2의 높이 초과는 실제 플레이에서도 확인.**

1280×720의 `draft-r4-picking`은 문서 높이 1023px이었다. 공용 카드 영역은 y=347∼806px, 내 보유 카드 영역은 y=806∼922px이다. 하단 카드의 가격과 보유 핸드를 확인하려면 스크롤해야 한다. 선택 제한 시간이 있는 단계에서 위 타이머, 아래 카드, 내 핸드를 따로 보게 된다.

실제 R2에서는 일반 닉네임과 정상 점수에서도 문서 높이 884px이었다. 스크롤 전 기준으로 내 보유 카드 영역은 약 y=667∼783px이며 하단 일부가 720px 밖이다. 검증용 큰 숫자만으로 생긴 현상은 아니다.

`r2-draft-arena.css:14`의 패널 최소 높이 560px, 별도로 쌓이는 제목과 상하 패딩, `r2-draft-arena.css:106`의 카드 영역 높이 및 간격, `r4-draft-arena.css:8`의 두 줄 공용 카드가 원인 범위다. 카드 16장을 8열로 유지하는 규칙 자체보다, 남은 세로 공간을 고려하지 않는 카드와 주변 요소의 합산 높이가 문제다.

### 5 R5 상점의 일곱 번째 카드가 좁은 PC 창에서 단독으로 내려감

**우선순위 P2. 검증용 화면에서 재현.**

1024×900과 1024×768의 `shop-r5-7`에서 내 카드가 6장과 1장으로 나뉜다. 내 카드 영역은 각각 약 607px와 597px인데, 88px 카드 7장과 8px 간격 6개의 합은 664px이다. 1024×768에서는 문서 높이도 805px가 된다.

`responsive.css:510`의 wrap, `responsive.css:511`의 고정 슬롯 폭, `responsive.css:520` 이하의 88px 카드와 2대1 패널 분할이 맞물린다. 기존 주석은 카드 수가 늘면 크기보다 줄바꿈을 허용하도록 되어 있으므로, 단순 누락뿐 아니라 현재 PC 배치 정책과 한 줄 요구 사이의 충돌이다. 상점과 보유 카드 규격을 같게 유지하면서 두 영역이 공유하는 카드 크기를 줄이거나 패널 분할 시점을 조정할 수 있다.

### 6 화면을 넘길 때 이전 세로 스크롤 위치가 남음

**우선순위 P2. 실제 싱글 플레이에서 재현.**

화면 아래의 라운드 결과 확인 버튼을 눌러 R1 순위표로 이동했을 때 `scrollY=139`가 유지되고 라운드 제목의 상단이 y=-45px에 있었다. 순위표에서 R2 드래프트로 이동한 후에도 `scrollY=151`, 제목 상단 y=-41px가 관측됐다. 사용자는 새 단계에 들어갔는데 제목을 보지 못하는 상태가 된다.

`App.tsx:224` 이후의 페이즈별 렌더링과 `ShowdownCinematic.tsx`의 전환 경로에서 해당 화면 변경에 맞춘 스크롤 및 포커스 복원을 확인하지 못했다. 모든 렌더링마다 스크롤을 되돌리는 것은 타이머나 사용자 읽기를 방해하므로, 페이즈나 매치 식별자가 실제로 바뀌는 시점에 한정할 필요가 있다.

### 7 내용이 넘치지 않아도 최종 쇼다운에 24px 스크롤이 생김

**우선순위 P2. 검증용 화면에서 재현.**

`showdown-r5-7`은 1280×720에서 문서 높이 744px, 1366×768에서 792px였다. 두 경우 모두 정확히 24px가 초과한다. `responsive.css:533`은 최종 쇼다운 최소 높이를 `100dvh - 24px`로 정하지만, `cinematic.css:1`의 위아래 24px margin은 남아 있어 총합이 viewport보다 24px 크다. 내용 크기와 별개로 스크롤을 만드는 계산 불일치다.

### 8 최종 순위표는 넓은 PC에서도 전체 순위가 한 화면에 들어오지 않음

**우선순위 P2 개선 후보. 검증용 화면 결과이며 실제 경기 종료까지 검증하지 않음.**

`final`은 1920×1080에서도 문서 높이가 1187px였다. `final-standings.css:6`의 기본 행 최소 높이가 104px이고 8개 행에 제목과 표 헤더가 더해진다. 라운드 순위표와 달리 최종 점수 분해를 제공하므로 스크롤 자체를 무조건 결함으로 단정하지는 않는다. 다만 마지막에 아래 순위와 다음 게임 조작을 빠르게 확인하려는 목적에는 현재 밀도가 낮다. 기본 행은 간결하게 하고 상세 점수는 이미 존재하는 팝오버에 맡기는 방식이 후보이며, 정보 삭제는 별도 판단이 필요하다.

## 공통 원인과 검토 해석

이번 검토는 화면 크기를 모바일과 PC 두 종류로만 나누지 않고, 실제 이용 가능한 너비와 높이, 현재 페이즈, 카드 수를 함께 비교했다. 또한 카드가 줄바꿈한 현상을 개별 카드의 고장으로만 보지 않고, 해당 프로필이나 패널이 어느 공간을 배정받는지부터 확인했다. 같은 컴포넌트라도 두 명 대결, 세 명 대결, 네 명 결승의 카드 영역은 다르며, 브라우저 창을 반으로 줄이거나 노트북에서 도구 모음을 열면 충분히 PC에서도 좁은 공간이 만들어진다. 해상도가 크다는 사실만으로 카드와 버튼에 사용 가능한 공간이 보장되지는 않는다.

가장 분명한 구조적 문제는 PC 높이 대응이 일부 라운드와 일부 범위에만 붙어 있다는 점이다. R5 매칭은 낮은 창에서 더 안정적인 7열 규칙을 사용하지만 높은 창에서는 기본 wrap으로 되돌아간다. R4에는 낮은 PC 높이에 대한 보정이 있으나 R1과 R2에는 동일한 전체 높이 예산이 없다. 이는 모바일 우선 원칙 자체의 문제가 아니라, 모바일 보정 이후 넓은 화면의 기본 규칙과 예외 조건을 하나의 기준으로 정리하지 못한 상태에 가깝다. 특정 해상도를 한 번 통과시키는 추가 예외만으로는 이와 같은 경계의 역전이 반복될 수 있다.

한편 상점은 고정 폭 카드와 패널 비율을 우선하고, 매칭 화면은 일부 조건에서 균등 그리드를 사용하며, 쇼다운은 라운드별로 카드 그리드와 상하 여백을 달리한다. 카드 디자인을 통일하는 것과 카드 외곽 픽셀 크기를 언제나 고정하는 것은 다른 요구다. 랭크와 문양의 순서, 비율, 테두리, 색상은 같게 두면서 실제 프로필 폭에 맞춰 크기를 정할 수 있다. 따라서 카드가 한 줄에 들어오게 하려면 커뮤니티 보드 규격을 포기해야 한다는 양자택일은 필요하지 않다. 다만 작은 프로필에 과도한 축소를 적용하면 가독성이 떨어지므로 최소 읽기 크기와 전환 기준을 함께 검토해야 한다.

세로 문제도 단순히 스크롤바를 숨기는 방식으로 해결하면 안 된다. 이미 R1에서 진행 버튼이 화면 밖으로 내려가고 R4에서 선택할 카드가 잘리는 실질적 문제가 확인됐다. 이때 overflow를 숨기면 눈에 보이는 스크롤바만 사라지고 조작할 수 없는 영역이 남는다. 반대로 모든 글자와 카드를 일괄 축소하면 넓은 PC 화면에서는 너무 작은 UI가 된다. 중요한 조작과 현재 정보를 먼저 배치하고, 제목 장식과 중복 설명, 큰 패딩부터 줄이는 순서를 가져야 한다. 특히 자동 진행되는 보드와 제한 시간 안에 선택해야 하는 공용 카드는 장식보다 우선한다.

순위표에서는 콘텐츠 높이와 sticky 조작바가 서로 독립적으로 결정되어 있다. 진행 버튼을 화면 안에 두는 목표는 달성했지만 다른 정보 위를 덮는 비용을 계산하지 않은 것이다. 실제 데이터에서도 나타났으므로 긴 이름을 제한하거나 숫자 표현을 바꾸는 것으로 대체 해결할 수 없다. 화면 전환 뒤 남는 스크롤 위치도 같은 문제를 증폭한다. 이 세 가지는 별개로 보이지만, 한 단계의 전체 구성을 viewport 안에서 어떻게 읽고 조작하는지까지 확인해야 한다는 공통 원인을 갖는다.

## 수정 제안과 완료 기준

아래는 승인 전 제안이다. 이 검토에서 구현하지 않았다.

1. **프로필 카드 줄 배치를 공통화한다.** R3 네 장, R4 다섯 장, R5 일곱 장의 행 정책을 화면 이름에만 종속시키지 말고 카드 개수와 프로필 폭을 함께 기준으로 삼는다. 특히 R5의 7열 규칙을 창 높이 800px 이하에만 한정하지 않는다. 완료 기준은 800×900, 960×900, 960×720에서 같은 카드 수가 같은 한 줄 구조를 유지하고, 테두리와 카드의 랭크 및 문양이 잘리지 않는 것이다. 모바일의 승인된 예외 배치는 별도로 보존해야 한다.

2. **쇼다운 전체에 남은 높이를 배분한다.** 제목, 프로필, 보드, 진행 버튼을 합친 실제 높이를 먼저 계산한 다음 간격을 조정한다. 특정 footer만 위로 끌어올려 다른 콘텐츠와 겹치게 하지 않는다. 기본 PC 기준은 1280×720과 1366×768이며 R1의 다음 매치 버튼까지 스크롤 없이 보여야 한다. 더 큰 화면에서는 같은 밀도를 강요하지 않고 여백을 복원한다. 커뮤니티 보드와 카드의 읽기 크기는 유지할 수 있는 범위에서 먼저 패딩과 장식 공간을 줄인다.

3. **R2의 두 RUN 표현을 단계별로 점검한다.** 종료된 RUN 요약, 현재 RUN 보드, 아직 공개하지 않은 보드가 동시에 차지하는 공간을 분리해 검토한다. 현재 RUN은 항상 viewport 안에 있어야 하고, 이미 종료된 RUN의 정보를 접는다면 승패와 보상은 계속 읽을 수 있어야 한다. 단순히 두 번째 보드를 숨기는 방식은 게임 이해를 훼손한다. RUN 1 결과, 카드 교체 중, RUN 2 턴과 리버, 최종 결과를 각각 측정해야 안정적으로 완료했다고 볼 수 있다.

4. **PC 순위표의 조작바와 표에 서로 다른 자리를 보장한다.** sticky 바를 유지하려면 그 높이만큼 콘텐츠 영역을 분리하거나 표 내부 스크롤을 명시적으로 설계한다. 한 화면 표를 목표로 한다면 제목과 표 헤더, 8개 행, 타이머, 히스토리, 진행 바를 합친 예산을 가져야 한다. 완료 기준은 실제 정상 점수와 긴 닉네임 데이터 모두에서 어느 행도 버튼 뒤로 숨지 않는 것이다. overflow를 숨기거나 하위 순위를 생략한 상태는 통과로 보지 않는다.

5. **드래프트에서 선택 정보의 동시 가시성을 확보한다.** 제한 시간이 보이는 동안 선택 가능한 모든 카드와 가격, 내 보유 핸드를 같은 화면에서 비교할 수 있도록 PC 높이 조건을 추가한다. R4의 16장을 유지하면서 카드 높이, 가격 버튼, 상태 문구와 두 줄 사이 간격을 함께 조정한다. 왼쪽 선택 순서 패널이 전체 높이를 불필요하게 밀어 올리지 않는지도 확인한다. 긴 이름만 쓰는 스트레스 케이스와 실제 AI 기본 이름을 모두 통과해야 하며, 선택 기능과 키보드 포커스도 유지해야 한다.

6. **상점의 패널 전환과 카드 규격을 함께 정한다.** 1024px에서 곧바로 2대1 패널과 88px 카드를 적용하면 R5의 일곱 번째 카드가 내려간다. 이 구간에서만 내 카드 영역을 넓히거나, 보유 카드와 판매 카드가 공유하는 크기를 동시에 조정하는 안을 비교할 수 있다. 한쪽 카드만 작게 만들어 과거 규격 불일치를 되살리면 안 된다. 완료 기준은 최소 필요 카드 수에서 한 줄 유지 여부를 확인하고, 구매와 판매 버튼 및 빈 슬롯의 기준선도 같이 맞는 것이다.

7. **페이즈 전환 시 스크롤과 포커스를 복원한다.** R1 결과와 R2 드래프트에 새로 들어갈 때 이전 매치의 스크롤 위치가 남지 않도록 전환 식별자를 기준으로 처리한다. 매초 바뀌는 타이머나 카드 효과에 반응해 반복 실행하면 사용자의 읽기를 방해하므로 금지한다. 히스토리 펼치기나 설정 모달을 닫는 것은 새 페이즈와 구분한다. 완료 기준은 아래쪽 진행 버튼을 누른 경우에도 새 제목과 핵심 안내가 첫 화면에서 보이고 키보드 사용자의 포커스가 유실되지 않는 것이다.

8. **최종 화면의 높이 산식을 정리한다.** R5 쇼다운의 최소 높이에서 이미 뺀 여백과 실제 margin을 중복 계산하지 않도록 하고, 720px와 768px에서 발생한 고정 24px 초과를 제거한다. 최종 순위표는 별도 목적의 화면이므로 무리하게 같은 CSS를 재사용하지 않는다. 순위, 이름, 카드, 총점을 우선하고 점수 분해는 기존 팝오버를 활용하는 후보를 검토한다. 확정된 정보 항목을 삭제하거나 점수 규칙을 변경하는 작업은 이번 UI 문제의 해결책에 포함하지 않는다.

9. **현재 레이아웃 검사의 누락을 보완한다.** `responsiveAudit.ts:37`은 다섯 장의 기대 행 수를 특별 검사하지만 일곱 장 매칭에는 같은 검사가 없다. 단순 overlap 검사로는 정상적인 flex 줄바꿈을 오류로 찾지 못한다. 카드 수별 기대 행 수, 조작바와 정보 행의 교차 영역, 마지막 중요 버튼의 viewport 이탈을 명시적으로 검증해야 한다. glow나 승리 도장처럼 의도적으로 바깥에 그리는 장식은 실제 콘텐츠와 분리해 오탐을 줄여야 한다.

10. **PC 경계와 실제 경로를 회귀 검증에 포함한다.** 1280×720, 1366×768, 1440×900, 1920×1080 외에 800×900과 960×900을 남긴다. 너비만 바꾸는 검증으로는 이번 높이 조건 역전을 찾기 어렵다. 768, 800, 1024 같은 주요 경계의 직전과 직후도 확인하고, 합성 화면을 통과한 뒤 실제 싱글 전환과 멀티의 타이머 및 준비 바를 별도로 검증한다. 영어, 긴 닉네임, 확대 배율과 402×874 모바일 회귀도 후속 수정의 완료 조건에 포함하는 것이 좋다.

## 테스트 결과와 남은 확인

`npm test -- src/ui/cinematicRendering.test.ts src/ui/ShowdownPrepPanel.test.ts src/ui/FinalResultsPanel.test.ts` 실행 결과는 **3개 파일, 56개 테스트 통과**다. 정적 렌더링과 표시 규칙 테스트이므로 CSS의 실제 픽셀 배치가 정상이라는 증거는 아니다. 이번에 발견한 화면 결함이 있어도 해당 테스트는 통과한다.

검토용 주요 조합에서 문서의 가로 넘침은 발견하지 못했다. R3 네 장과 R4 다섯 장의 프로필 카드는 검사한 PC 크기에서 한 줄을 유지했다. 시작 메뉴와 설정 창은 실제 1280×720에서 조작 가능했고 설정 창의 내부 스크롤과 닫기 버튼은 동작했다. 설정 내부 스크롤은 제한 시간 게임 화면의 콘텐츠 이탈과 구분했다.

실제 게임 전체 5라운드 완주, 실제 멀티 방, 관전자와 재접속, 영어 UI, 125퍼센트 및 150퍼센트 확대, Chrome과 Edge 및 Safari 간 비교, 운영 iframe은 미검증이다. 새 코드를 작성하지 않았으므로 전체 테스트, Workers 테스트, lint와 빌드는 실행하지 않았다. 실행하지 않은 항목을 통과로 간주하지 않는다.

수정 우선순위는 프로필 한 줄 배치와 진행 버튼 및 선택 카드의 가시성, 순위표 가림, 화면 전환 복원, 최종 결과와 여백 정리 순이다. 본 문서는 재현 결과와 제안만 기록하며 게임 방향이나 UI 변경을 승인한 결정 문서는 아니다.

### 반응형 기준과 변경 파일

- `holto-chess/src/ui/responsive.css`: 기존 경계인 769px 이상을 PC 배치로 유지했다. 높이 800px 이하는 간격·타이머·작은 카드의 밀도를 보완한다. 상점은 PC에서도 2:1 패널을 사용하되 `cqw`로 페이지 폭에 맞춰 보유/마켓의 공통 카드 크기를 결정한다. 카드 디자인과 랭크/문양 순서는 바꾸지 않는다.
- 768px 이하 모바일은 기존 배치를 유지하며 상점 카드 수별 폭 계산을 보완했다. 높이 700px 이하에서만 상점·드래프트·R2 보드의 여백과 조작 크기를 추가 조정했다. 402×874가 기본 확인 대상이며 360×660도 별도로 통과했다. 스크롤바를 숨겨 콘텐츠를 자르는 방식은 쓰지 않았다. 사용자가 펼친 히스토리나 확대 설정에서는 필요한 스크롤을 허용한다.
- `GameViewportReset.tsx`, `viewportTransition.ts`: 표시 화면 식별자 변경 시에만 복원한다. 타이머 tick, 같은 드래프트의 픽 진행, 같은 매치의 RUN 프레임 변경에는 초기화하지 않는다. 열린 모달의 포커스는 가져오지 않는다.
- `App.tsx`, `OnlineApp.tsx`, `ShowdownCinematic.tsx`: 싱글/멀티 페이즈, 매칭, 쇼다운, 테이블 대기 화면에 같은 복원 경로를 적용했다. `ResponsivePreview.tsx`는 단일 검증 상태에 같은 경로를 연결했다.
- `responsiveAudit.ts`: 실제 배치 좌표로 카드 줄 수를 판단해 발광 transform의 오탐을 줄이고, PC 7장 줄바꿈 및 진행 바/순위 행 겹침 검사를 추가했다.
- `viewportTransition.test.ts`, `responsiveAudit.test.ts`: 아래 9개 회귀 테스트를 추가했다. `product_doc/TODO.md`의 `UI-DESKTOP-021` 완료 상태를 갱신했다. 기존 다른 작업자의 미추적 파일은 보존했다.

### 브라우저 검증

로컬 React 서버의 실제 컴포넌트 검증 페이지에서 **13개 상태 × 10개 크기 = 130개 조합**을 검사했다.

- 상태: `match-r5-7`, `shop-r5-7`, `showdown-r1-2`, `showdown-r2-run1-result`, `showdown-r2-run2-river`, `showdown-r3-4`, `showdown-r4-5`, `showdown-r5-7`, `results-r1`, `results-r2`, `draft-r2`, `draft-r4-picking`, `final`.
- 크기: 1280×720, 1366×768, 1440×900, 1920×1080, 1024×768, 960×900, 960×720, 800×900, 402×874, 360×660 CSS px.
- 전체 검사에서 마지막으로 남았던 360×660 R4 드래프트의 2px 초과는 순서 목록 간격을 조정하고 해당 조합을 재검사하여 문서 높이 660px를 확인했다. 최종적으로 검사한 조합에서 문서 가로/세로 넘침, 주요 영역의 화면 이탈, PC 7장 카드 줄바꿈이 없었다. 이것은 지정한 상태와 뷰포트에 대한 결과이며 모든 게임 상태의 보장은 아니다.
- 대표 측정: 1280×720 검증 R2 순위표 y=240–594, 진행 바 y=653–712. R4 드래프트 카드 y=259–542, 보유 핸드 y=542–640. 360×660 R5 상점 진행 바 y=597–653. 402×874 R2 순위표 진행 바 y=671–729.

실제 싱글 플레이는 1280×720에서 어빌리티 선택·공개, 카드 구매, R1 매치 3회, R1 순위표, R2 드래프트 진입까지 다시 진행했다. 실제 R1 첫 매치 진행 버튼은 수정 전 y=760–810/문서 859px에서 수정 후 y=596–646/문서 720px로 들어왔다. 실제 R1 순위표는 y=201–555, 진행 바 y=614–671, 문서 720px였다. 히스토리를 펼쳐 `scrollY=528`인 상태에서 라운드 마감 버튼으로 R2에 진입하면 `scrollY=0`, 문서 720px, 새 페이지 포커스가 확인됐다.

### 자동 검증

- `npm test`: **90개 파일 / 631개 테스트 통과**.
- `npm run test:workers`: **5개 파일 / 33개 테스트 통과**. 로컬 관리자 secret 미설정, Wrangler 로그 파일 권한 및 정적 분석 경고가 있었지만 테스트는 모두 실행되어 종료 코드 0으로 완료됐다.
- `npm run lint`: 통과.
- `npm run build`: 최종 수정 후 통과. Wrangler 타입 생성, 앱 `tsc -b`, Worker `tsc -p tsconfig.worker.json`, Vite 클라이언트·Worker 빌드를 포함한다. 로컬 관리자 secret 미설정 경고는 남아 있으며 실제 관리자/배포 검증을 뜻하지 않는다.
- 추가 회귀 9개: 스크롤 양축 복원/포커스, 열린 모달 포커스 보존, 화면 미마운트 무동작, 숨김 식별자 렌더링, 높은 PC 창의 6+1 감지, 7장 한 줄 허용, 모바일 예외, 진행 바 순위 행 가림 감지, 정상 문서 흐름 허용.
- 첫 전체 테스트와 빌드는 최신 코드에 이미 선언된 `@discord/embedded-app-sdk@2.5.0`이 로컬에 설치되지 않아 실패했다. 기존 잠금 버전으로 의존성을 설치한 뒤 재실행하여 위 결과를 얻었다. 의존성 버전이나 package 파일의 실질 변경은 없다. 새 검증 테스트의 재귀 반환 타입 추론 오류도 명시적 타입을 추가한 뒤 최종 타입 검사에서 해소했다.

### 남은 확인 및 배포 상태

전체 5라운드 실제 완주, 실제 멀티 방/관전자/재접속, 영어 UI, 브라우저 확대 125%·150%, 다른 브라우저 엔진과 Discord/CrazyGames 운영 iframe은 미검증이다. 특히 최종 결과 검증용 래퍼는 실제 종료 도구와 재경기 패널을 모두 재현하지 않으므로 최종 페이지 전체를 실경기로 확인한 것으로 간주하지 않는다. 카드·표·핸드 배치는 실제 컴포넌트를 사용한 검증 결과다.

커밋·push·운영 배포는 하지 않았다. 화면 확인은 최신 main을 바탕으로 수정한 로컬 작업본에서 수행했다.
