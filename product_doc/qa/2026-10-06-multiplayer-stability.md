# 멀티플레이 연결 및 공개 알람 안정화 — 2026-10-06

기준 main: `e2e56d16ca515aedf44b60e78c0061e715f68fa8`.
별도 복제본에서 수정·검증했으며 원본 작업 폴더의 다른 미완료 변경은 포함하지 않았다.

## 재현과 수정

1. **WebSocket이 OPEN인 채 수신만 끊기는 경우**
   - 로컬 프록시에서 한 클라이언트의 수신만 차단했다. 기존 클라이언트는 R1 연출 화면에 60초 이상 머물렀지만 다른 클라이언트와 서버는 진행했다.
   - 티켓 요청, 연결, JOIN, 첫 PLAYER_VIEW에 시간 제한을 적용했다. 활동 중 시계 요청에 대한 최신 PLAYER_VIEW가 도착하지 않으면 연결을 교체한다. CLOCK_SYNC만 도착한 경우는 상태 복구로 간주하지 않는다.
   - 단조 시계 기준 응답 제한은 15초, 재시도는 최대 5회와 제한된 backoff를 사용한다. 이전 연결의 늦은 이벤트와 역순 view는 무시하고 같은 revision의 최신 공개 view는 수용한다.
   - 브라우저 재현에서 첫 무응답 probe 약 15.99초 후 기존 소켓을 교체했고, 수신 복구 후 새로고침 없이 현재 경기에 합류했다.
   - 숨긴 탭은 주기 요청을 멈추고 복귀/긴 이벤트 루프 정지 후에는 새 응답 시간을 부여한다. 세션 교체·인증 거절은 자동으로 되찾지 않는다. 로비와 공개 완료 결과 화면에 주기 트래픽을 추가하지 않았다.

2. **broadcast 처리 중 공개 종료 경계를 지나는 경우**
   - workerd에서 projection 이후 시각이 종료 경계를 지나도록 재현했다. 기존 구현은 최종 공개 대신 약 30초 뒤 확인 barrier를 예약할 수 있었다.
   - 실제로 projection한 시각을 다음 알람 계산에 전달하여 아직 보내지 못한 공개 경계를 놓치지 않도록 했다.

3. **다른 요청이 이미 도래한 공개 알람보다 먼저 처리되는 경우**
   - SYNC_CLOCK 등의 요청이 도래한 알람을 이후 만료 시각으로 덮는 조건을 workerd 회귀 검사로 재현했다.
   - 큐에서 기다리는 도래한 알람을 보존한다. 실행 중인 알람의 getAlarm 동작은 Cloudflare의 [Durable Object alarm 명세](https://developers.cloudflare.com/durable-objects/api/alarms/)를 따른다.

이 재현은 정지를 일으킬 수 있는 경로를 확인한 것이다. 사용자에게 발생한 과거 운영 장애 전부가 같은 원인이었다고 확정하지 않는다.

## 유지한 조건

- 게임 규칙, protocol 15, 기존 1.5초 cinematic prefetch, 최종 standings/end gating, 전원 인간 탈락 시 마지막 연출 + 5초 대기를 변경하지 않았다.
- 로컬 프록시·fixture·DB·장애 주입 도구는 저장소 밖에 두었으며 production 출력에 포함되지 않는 것을 확인했다.
- 선택적 개발 진단은 연결 세대·phase·round·revision·시각 등 메타데이터만 기록한다. 티켓·세션 토큰·카드·전체 payload를 기록하지 않는다.
- package.json, package-lock.json, Wrangler 설정과 계정 권한을 변경하지 않았다.

## 자동 검증

기존 lockfile의 의존성을 `npm ci --ignore-scripts`로 복원한 뒤 실행했다.

| 검사 | 결과 |
|---|---|
| `npm test -- --maxWorkers=2` (Discord 포함) | 101개 파일, 701개 테스트 통과 |
| `npm run test:workers -- --maxWorkers=1` | 7개 파일, 42개 테스트 통과 |
| `npm run lint` | 통과 |
| `npm run build` | 타입 생성, 앱/Worker 타입 검사, production 번들 생성 통과 |
| `git diff --check` | 통과 |

전송 회귀 검사는 무응답 OPEN 소켓, 티켓/연결/JOIN/view 정지, 늦은 이전 연결 이벤트, 같은 revision 공개 갱신, 재시도 상한, 종료 코드, 숨김/복귀, 이벤트 루프 정지와 wall-clock 변경을 포함한다. Worker에는 공개 알람 두 결함의 회귀 검사를 추가했다.

기존 Worker 통합 검사의 두 가정을 바로잡았다. NET001 이전의 "매치 시작 전 payload 없음" 조건 대신 이미 승인된 1.5초 prefetch 경계 전후와 정확한 공개 elapsed를 검사한다. 또한 NET002 전원 탈락으로 봇 정산이 끝난 경로를 일반 final cinematic 경로와 구별한다. 최종 결과 조기 공개 차단 검사는 유지한다. 비동기 수신은 해당 presentation epoch의 payload를 검사한다.

기존 lock의 npm audit 결과는 moderate 4건, high 2건이다. high 전이 의존성은 source-map-js와 undici이며 이번 수정에서 버전 변경이나 audit fix는 하지 않았다.

## 실제 브라우저 검증과 한계

로컬 Cloudflare Worker에 서로 다른 origin/storage를 가진 Chrome 클라이언트 두 개를 연결했다. 실제 게임 시계는 단축하지 않았다.

- R1~R5 → 일치하는 최종 순위표 → 같은 방 재경기 R1 진입 확인.
- 수신만 중단하는 장애의 자동 복구, 650ms 지연 수신, 관전 대상 변경, 명시적 연결 종료 후 자동 복구와 관전 선택 유지 확인.
- 첫 경기는 개발 hot reload와 저장된 방 수동 복귀가 포함됐다. 이후 재경기는 새 전송 코드로 새로고침 없이 완주했지만 Worker 수정 hot update가 있었다. 이를 고정된 production 빌드의 연속 내구 시험으로 간주하지 않는다.

다음 **두 항목은 실제 브라우저 미검증**이다. 브라우저 제어 도구가 후속 실행 환경에서 사라졌고, 대체 제어 경로로 우회하지 않았다.

1. 전원 인간 탈락 → 마지막 연출 + 5초 → 결과 → 재경기 화면 흐름. 자동 회귀와 로컬 재현 상태 준비는 완료했지만 실제 화면 확인은 완료하지 못했다.
2. 실제 background 탭 정지/제한 후 foreground 복귀. 모의 hidden/resume·이벤트 루프 정지 검사는 통과했지만 실제 브라우저 검증을 대신하지 않는다.

이 두 항목을 미검증으로 명시한 상태의 main 커밋·일반 푸시 및 연결된 자동 운영 반영이 사용자에게 승인됐다. 별도 수동 배포는 범위에 포함하지 않는다. 운영 방 조작과 운영 부하 검사는 수행하지 않는다.
